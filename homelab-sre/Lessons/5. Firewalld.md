# Lezione 5 — Firewall: netfilter, nftables, firewalld

> **Attenzione prima di iniziare**: un firewall configurato male ti può chiudere fuori dal sistema. Lavora da tastiera/monitor collegati direttamente, oppure usa sempre l'opzione `--timeout` per le regole di test (la vedi nella pratica): scade da sola e ripristina lo stato precedente anche se ti sei chiuso fuori.

## Teoria (45')

### I tre livelli: netfilter, nftables, firewalld

Il termine "firewall" su Linux indica tre cose diverse, impilate una sopra l'altra. Confonderle è l'errore più comune:

```
firewalld          ← gestore ad alto livello (zone, servizi): quello che usi tu
   │
nftables           ← framework di regole (comando `nft`), successore di iptables
   │
netfilter          ← il motore dentro il kernel che intercetta davvero i pacchetti
```

- **netfilter** è il sottosistema del kernel: agisce in punti precisi del percorso di un pacchetto (gli "hook"). Non lo configuri direttamente.
- **nftables** è lo strumento per scrivere regole in netfilter. Ha sostituito iptables (che su Fedora esiste ancora come comando di compatibilità, `iptables-nft`, ma scrive regole nftables sotto).
- **firewalld** è un demone che ti permette di ragionare per *zone* e *servizi* invece che per singole regole, e traduce tutto in nftables (backend di default su Fedora da anni). Le modifiche si applicano **senza interrompere le connessioni esistenti**, cosa che con script di regole manuali è molto più delicata.

Regola pratica: usa firewalld per la configurazione, `nft` solo per *osservare* cosa è stato generato.

### Come viaggia un pacchetto (versione semplificata)

```
              ┌─────────────► INPUT ──► processo locale
rete ─► PREROUTING                              │
              └─► FORWARD ──► POSTROUTING ◄── OUTPUT
                  (routing: il pacchetto non è per me)
```

- **INPUT**: pacchetti destinati a questa macchina (es. SSH verso il tuo PC).
- **OUTPUT**: pacchetti generati da questa macchina.
- **FORWARD**: pacchetti che *attraversano* la macchina verso un'altra destinazione — il caso delle VM e dei container dietro NAT.
- **POSTROUTING/PREROUTING**: dove avviene il NAT.

Perché conta per te: tra poco avrai VM e container, e il loro traffico passa spesso da FORWARD, non da INPUT. Un firewall che "sembra a posto" per i servizi dell'host può comunque bloccare (o lasciar passare) il traffico delle VM.

### Zone: il concetto centrale di firewalld

Una **zona** è un livello di fiducia con una propria lista di cosa è permesso. Ogni interfaccia (o ogni rete sorgente) è assegnata a *una* zona.

| Zona | Fiducia | Comportamento tipico |
|---|---|---|
| `drop` | nulla | scarta tutto in ingresso, senza rispondere |
| `block` | nulla | rifiuta in ingresso con messaggio ICMP |
| `public` | bassa | solo servizi esplicitamente abilitati |
| `internal` / `home` / `work` | media | rete locale, più servizi permessi |
| `trusted` | totale | accetta tutto |

Fedora ha zone proprie come default:

- **FedoraWorkstation** (edizione Workstation): permette SSH e alcuni servizi, **ma anche tutte le porte TCP/UDP da 1025 a 65535**. È una scelta pensata per un desktop, non per un server: significa che qualsiasi servizio tu metta in ascolto su una porta alta è raggiungibile dalla rete, firewall o no.
- **FedoraServer** (edizione Server): molto più restrittiva (SSH, Cockpit, DHCPv6 client).

Controlla subito quale hai: è la prima cosa da sapere sul tuo sistema (vedi pratica).

### Servizi, porte, rich rules

- **Servizio**: un nome che raggruppa porte e protocolli (`ssh` = 22/tcp). Le definizioni sono file XML in `/usr/lib/firewalld/services/` (di sistema) e `/etc/firewalld/services/` (tue).
- **Porta**: apri direttamente `8080/tcp`. Più rapido, meno leggibile nel tempo.
- **Rich rule**: regola più espressiva che combina sorgente, destinazione, servizio, azione e logging.

### Runtime vs permanent

È il punto che frega tutti all'inizio. firewalld ha **due configurazioni**:

- **Runtime**: attiva ora, sparisce al `reload` o al riavvio.
- **Permanent**: salvata su disco, ma *non attiva* finché non fai `--reload`.

```bash
sudo firewall-cmd --add-service=http                 # solo runtime
sudo firewall-cmd --permanent --add-service=http     # solo permanent (non attiva ora!)
sudo firewall-cmd --runtime-to-permanent             # copia il runtime nel permanente
sudo firewall-cmd --reload                           # ricarica il permanente (perde il runtime non salvato)
```

Flusso consigliato per lavorare in sicurezza: **prova prima in runtime** (con `--timeout` se rischioso), verifica che funzioni, poi `--runtime-to-permanent`.

### Due interazioni da conoscere già adesso

- **libvirt** (Fase 2) crea la propria zona `libvirt` e le regole per il suo bridge NAT `virbr0`. Un bridge che crei tu (come `br0` della lezione 4) va invece assegnato a una zona da te.
- **Docker** (Fase 3) scrive le *proprie* regole di forwarding/NAT e le porte pubblicate con `-p` possono **bypassare le regole di zona** di firewalld. Su Fedora Docker crea una zona `docker`, ma conviene verificare empiricamente cosa è raggiungibile, non fidarsi di `--list-all`. Lo riprenderemo alla lezione 10.

## Pratica (75-90')

### 1. Osserva lo stato di partenza

```bash
sudo firewall-cmd --state                       # deve rispondere "running"
sudo firewall-cmd --get-default-zone
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all                    # zona di default, con servizi e porte
```

Annota: quale zona di default hai? `br0` (lezione 4) in che zona è finito? Se vedi `ports: 1025-65535/tcp 1025-65535/udp` sei in FedoraWorkstation, con quanto detto sopra.

Guarda anche come questo diventa nftables:

```bash
sudo nft list ruleset | head -80
sudo nft list tables                            # cerca "table inet firewalld"
```

Non devi capire ogni riga: l'obiettivo è vedere che le zone sono diventate *chain* con regole concrete.

### 2. Crea un servizio in ascolto per fare test

Hai bisogno di qualcosa di raggiungibile da testare. Servizio web minimale su una porta alta:

```bash
mkdir -p ~/homelab/fw-test && cd ~/homelab/fw-test
echo "ciao dal lab" > index.html
python3 -m http.server 8080 --bind 0.0.0.0
```

In un secondo terminale:

```bash
ss -tlnp | grep 8080                            # conferma che è in ascolto su 0.0.0.0:8080
curl http://localhost:8080                      # dalla stessa macchina
```

> **Test da un altro dispositivo**: `localhost` passa dall'interfaccia `lo`, che il firewall non filtra. Per verificare davvero le regole devi provare **da un altro PC o dal telefono** sulla stessa rete: `curl http://192.168.1.50:8080`. Tutti i test di questa lezione vanno fatti così.

Dal secondo dispositivo, nella zona di default Fedora Workstation, probabilmente risponde. Tienilo a mente: è l'apertura implicita di cui parlavamo.

### 3. Crea una zona dedicata al laboratorio

Invece di modificare la zona di default, crei una zona tua e assegni il bridge `br0` a essa.

```bash
sudo firewall-cmd --permanent --new-zone=homelab
sudo firewall-cmd --reload
sudo firewall-cmd --permanent --zone=homelab --set-target=DROP
```

`DROP` come target significa: **tutto ciò che non è esplicitamente permesso viene scartato**. Approccio *default deny*, quello giusto per un ambiente da SRE.

Assegna `br0` alla zona. Con NetworkManager il modo corretto (persistente) è:

```bash
sudo nmcli connection modify br0 connection.zone homelab
sudo nmcli connection up br0
sudo firewall-cmd --get-active-zones            # br0 deve comparire sotto "homelab"
```

> Se sei da SSH sulla rete di `br0` puoi perdere la sessione qui: la nuova zona ha target DROP e ancora nessun servizio. Fai questo passaggio da console locale, oppure salta al punto 4 e abilita SSH *prima* di assegnare l'interfaccia.

### 4. Abilita solo ciò che serve, e solo per chi serve

Prima di tutto SSH, ma limitato alla tua rete (adatta gli indirizzi):

```bash
sudo firewall-cmd --permanent --zone=homelab --add-source=192.168.1.0/24
sudo firewall-cmd --permanent --zone=homelab --add-service=ssh
sudo firewall-cmd --reload
sudo firewall-cmd --zone=homelab --list-all
```

Poi una **rich rule** più stretta: SSH solo da un indirizzo (il tuo PC principale), con log dei tentativi respinti:

```bash
sudo firewall-cmd --permanent --zone=homelab --remove-service=ssh
sudo firewall-cmd --permanent --zone=homelab --add-rich-rule='rule family="ipv4" source address="192.168.1.10" service name="ssh" accept'
sudo firewall-cmd --reload
```

Verifica da due dispositivi diversi: da `192.168.1.10` SSH funziona, dagli altri no.

### 5. Definisci servizi custom per ciò che costruirai nelle fasi successive

Invece di aprire "la porta 5000" senza contesto, dai un nome a ciascun componente. Qui prepari tre servizi che userai più avanti:

```bash
# Registry Docker privato (Fase 3)
sudo firewall-cmd --permanent --new-service=homelab-registry
sudo firewall-cmd --permanent --service=homelab-registry --set-description="Docker registry privato del lab"
sudo firewall-cmd --permanent --service=homelab-registry --add-port=5000/tcp

# Stack di osservabilita (Fase 5)
sudo firewall-cmd --permanent --new-service=homelab-grafana
sudo firewall-cmd --permanent --service=homelab-grafana --add-port=3000/tcp

sudo firewall-cmd --permanent --new-service=homelab-prometheus
sudo firewall-cmd --permanent --service=homelab-prometheus --add-port=9090/tcp

sudo firewall-cmd --reload
sudo firewall-cmd --info-service=homelab-registry
```

Non li abiliti ancora nella zona: li attiveremo quando i componenti esisteranno. Il vantaggio è che la lista di cosa è aperto, e *perché*, sarà leggibile e versionabile (i file stanno in `/etc/firewalld/services/`).

### 6. Esperimento di rottura controllata (con rete di sicurezza)

Simula l'errore classico: una regola che blocca proprio te. Usa `--timeout` così si autodistrugge.

```bash
sudo firewall-cmd --zone=homelab --add-rich-rule='rule family="ipv4" source address="192.168.1.10" drop' --timeout=60
```

Dal dispositivo `192.168.1.10`, prova SSH o `ping`: smette di rispondere. Dopo 60 secondi la regola sparisce e tutto torna normale. Osserva:

```bash
sudo firewall-cmd --zone=homelab --list-rich-rules       # compare, poi sparisce
```

Questo è il modo *giusto* di testare regole rischiose in produzione: runtime con timeout, mai direttamente permanente.

### 7. Logga ciò che viene scartato

```bash
sudo firewall-cmd --set-log-denied=all
# da un altro dispositivo, prova a collegarti a una porta chiusa, poi:
sudo journalctl -k --since "5 min ago" | grep -i -E "REJECT|DROP"
sudo firewall-cmd --set-log-denied=off                   # a fine esperimento
```

Le righe nel journal mostrano sorgente, destinazione e porta del pacchetto bloccato: è la base per diagnosticare un "non riesco a connettermi al servizio" quando sospetti il firewall.

### 8. Salva e documenta

Se tutto è come vuoi (e solo allora):

```bash
sudo firewall-cmd --runtime-to-permanent
sudo firewall-cmd --zone=homelab --list-all > ~/homelab/fw-zona-homelab.txt
```

Aggiungi quel file al repo del progetto, con una nota su **cosa hai aperto e perché**: è documentazione di sicurezza che ti tornerà utile.

### 9. Pulizia dell'esperimento

```bash
# ferma il server di test con Ctrl+C
rm -rf ~/homelab/fw-test
```

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| Ho aperto una porta ma non funziona | Hai usato `--permanent` senza `--reload`, oppure hai aperto la zona sbagliata (l'interfaccia è in un'altra zona: `--get-active-zones`) |
| Funziona da `localhost` ma non da altri dispositivi | Il traffico su `lo` non è filtrato; il firewall blocca solo il traffico in arrivo dalla rete. Testa sempre da un altro host |
| Dopo il reboot la regola è sparita | Era solo in runtime: serve `--runtime-to-permanent` o `--permanent` |
| Container o VM raggiungibili anche se il firewall "dice di no" | Docker/libvirt aggiungono regole proprie (nat, forward) che non passano dalle zone che stai guardando |
| Il servizio è in ascolto ma `connection refused` | Il firewall non c'entra (con DROP avresti un timeout, non un rifiuto): il processo ascolta solo su `127.0.0.1`. Controlla con `ss -tlnp` |
| `connection timed out` | Segnale tipico di DROP: un firewall scarta in silenzio. `refused` = porta chiusa o REJECT; `timeout` = DROP o instradamento mancante |
| Ti sei chiuso fuori da SSH | Ecco perché si lavora in runtime con `--timeout`, o da console locale |
