# Lezione 6 — DNS: concetti base, zone, record

> **Prima di iniziare**: le VM non esistono ancora (arrivano nelle lezioni 7-9). In questa lezione costruisci il DNS del laboratorio e lo verifichi con `dig`, assegnando ai nomi gli indirizzi IP **che le VM avranno più avanti**. Quando creerai le VM, basterà dar loro l'IP statico previsto e i nomi funzioneranno subito.

## Teoria (45')

### Cos'è il DNS e come funziona una risoluzione

Il DNS (Domain Name System) traduce nomi (`master.lab`) in indirizzi (`192.168.1.60`) e, al contrario, indirizzi in nomi. È un database distribuito e gerarchico: nessun server conosce tutto, ognuno conosce la sua parte e sa a chi chiedere il resto.

La gerarchia si legge **da destra a sinistra**:

```
www.example.com.
 │    │      │  └─ radice (root), il "." finale quasi sempre omesso
 │    │      └──── TLD (top-level domain): com
 │    └─────────── dominio di secondo livello: example
 └──────────────── host: www
```

Il nome completo, con il punto finale, si chiama **FQDN** (Fully Qualified Domain Name): `www.example.com.`

Cosa succede quando chiedi `www.example.com` (cache vuota):

```
App → stub resolver → resolver ricorsivo ──► root server    "chi gestisce .com?"
                            │            ──► server .com     "chi gestisce example.com?"
                            │            ──► server di        "www.example.com = 93.184.x.x"
                            │                example.com
                            ◄── risposta (messa in cache) ────┘
```

### I tre ruoli da non confondere

| Ruolo | Cosa fa | Esempi |
|---|---|---|
| **Stub resolver** | Il "client" DNS dentro l'host: non risolve, inoltra la domanda a un resolver ricorsivo | `systemd-resolved`, la libc (`getaddrinfo`) |
| **Resolver ricorsivo** (o forwarder) | Fa il lavoro di ricerca per conto del client e mette in **cache** le risposte | router di casa, `1.1.1.1`, `dnsmasq` che inoltra |
| **Server autoritativo** | Ha la risposta "ufficiale" per una zona e la serve dai propri dati | BIND con una zona, i server DNS del tuo registrar |

`dnsmasq` è un tuo piccolo ibrido: **autoritativo** per il dominio `.lab` (risponde dai suoi dati locali) e **forwarder con cache** per tutto il resto.

### Zone, delegazione, FQDN

Una **zona** è la porzione dello spazio dei nomi di cui un server è responsabile. `example.com` può essere una zona; `lab` sarà la tua. Una zona può **delegare** una parte a un altro server (record `NS`): è così che `.com` indica chi gestisce `example.com`.

Ogni zona ha un record **SOA** (Start of Authority) con parametri amministrativi (serial, tempi di refresh) e almeno un record **NS**.

### I record che incontrerai

| Tipo | Significato | Esempio | Dove lo ritroverai |
|---|---|---|---|
| **A** | nome → IPv4 | `master.lab → 192.168.1.60` | ovunque |
| **AAAA** | nome → IPv6 | `master.lab → fd00::60` | ovunque |
| **CNAME** | alias di un altro nome | `registry.lab → bastion.lab` | spostare un servizio senza cambiare i client |
| **PTR** | IP → nome (reverse lookup) | `60.1.168.192.in-addr.arpa → master.lab` | log, SSH, diagnostica |
| **NS** | server autoritativi della zona | `lab → ns1.lab` | delegazioni |
| **SOA** | parametri della zona | serial, refresh, retry... | zone file |
| **MX** | server di posta | `10 mail.example.com` | solo posta |
| **TXT** | testo libero | `"v=spf1 ..."` | verifiche di dominio, SPF |
| **SRV** | servizio, porta, priorità | `_ssh._tcp.lab → bastion.lab:22` | **service discovery**, etcd, Kubernetes |

Due regole che mordono: un **CNAME non può coesistere con altri record sullo stesso nome**, e non si usa sull'apex della zona.

### TTL e caching: il tempo è parte della risposta

Ogni record ha un **TTL** (time-to-live, in secondi): per quanto chi lo riceve può tenerlo in cache senza richiederlo di nuovo.

- TTL alto → meno traffico, ma una modifica impiega più tempo a propagarsi.
- TTL basso → modifiche rapide, più query.
- Esiste anche il **negative caching**: anche "questo nome non esiste" (NXDOMAIN) viene messo in cache.

Conseguenza pratica da SRE: se devi migrare un servizio, **abbassi il TTL prima**, aspetti che scada il vecchio valore, poi cambi il record. Fare il contrario è una classica causa di "per metà degli utenti funziona, per l'altra metà no".

### Un esempio di zone file

`dnsmasq` non usa zone file (si configura con direttive), ma BIND sì, ed è il formato "storico" che trovi in giro. Ecco come apparirebbe la tua zona `lab`:

```
$TTL 300
@       IN  SOA ns1.lab. admin.lab. (
            2026100601  ; serial (convenzione AAAAMMGGNN)
            3600        ; refresh
            900         ; retry
            604800      ; expire
            300 )       ; negative caching TTL

        IN  NS   ns1.lab.

ns1       IN  A      192.168.1.50
hv        IN  A      192.168.1.50
bastion   IN  A      192.168.1.51
master    IN  A      192.168.1.60
worker1   IN  A      192.168.1.61
registry  IN  CNAME  bastion
```

Attenzione al punto finale: `ns1.lab.` è un FQDN assoluto; `bastion` senza punto significa "bastion + il nome della zona". Dimenticare il punto finale è l'errore più classico nei zone file.

### Dove vive il DNS dentro Fedora

Un'app non parla direttamente con un server DNS. Il percorso è:

```
applicazione ──► libc (getaddrinfo) ──► /etc/nsswitch.conf decide l'ordine delle fonti
                                              │
                      ┌───────────────────────┼──────────────────┐
                      ▼                       ▼                  ▼
                 /etc/hosts            systemd-resolved     (altre fonti)
                                       stub 127.0.0.53
                                              │
                                              ▼
                              DNS configurati per interfaccia
                                  (da NetworkManager)
```

Dettagli importanti su Fedora:

- **`systemd-resolved`** è lo stub resolver di default. Ascolta su `127.0.0.53:53` e `/etc/resolv.conf` è un link simbolico che punta a lui.
- **NetworkManager** gli comunica quali DNS usare per ogni interfaccia (per questo la configurazione si fa con `nmcli`, non editando `/etc/resolv.conf`).
- **`dig` salta tutto questo**: interroga direttamente il server DNS indicato. `ping`, `curl`, `ssh` invece seguono `nsswitch` e `resolved`. Se `dig` funziona ma `ping` no (o viceversa), il problema è nel livello intermedio, non nel server.

### dnsmasq, BIND, CoreDNS: quale usare

| | dnsmasq | BIND (`named`) | CoreDNS |
|---|---|---|---|
| Peso/complessità | Leggerissimo, un file di config | Pesante, il riferimento "da manuale" | Medio, a plugin |
| Zone file | No (direttive) | Sì | Sì (plugin `file`) |
| Cache/forwarder | Sì | Sì | Sì |
| DHCP integrato | Sì | No | No |
| Quando usarlo | Laboratori, reti piccole | Zone autoritative serie, delegazioni, DNSSEC | **È il DNS interno di Kubernetes** |

Scegliamo **dnsmasq** come percorso principale: è il più rapido per ottenere un risultato utile. In fondo trovi un bonus opzionale con BIND, per vedere come funziona una zona vera. CoreDNS lo incontrerai alla lezione 13.

> **Attenzione al DHCP**: dnsmasq può fare anche da server DHCP, ma **non attivarlo** sulla tua rete di casa: due server DHCP sullo stesso segmento (il tuo router e dnsmasq) entrano in conflitto e assegnano indirizzi a caso. Qui usi dnsmasq solo per il DNS.

### Che nome di dominio scegliere

Il piano usa `.lab`, e per un laboratorio va bene. Alcuni criteri per scegliere con cognizione:

- **Evita `.local`**: è riservato al multicast DNS (mDNS/Avahi) e crea comportamenti strani.
- **`.lab` non è un TLD riservato**: in teoria potrebbe un giorno essere delegato davvero. Un'alternativa ufficialmente riservata per uso privato è **`.internal`** (riservato da ICANN nel 2024); per le reti domestiche esiste anche `home.arpa` (RFC 8375).
- Cambiare dominio in seguito costa poco in questo setup (una riga di configurazione), quindi usa `.lab` per ora senza problemi.

## Pratica (75-90')

### 0. Pianifica gli indirizzi

Prima di scrivere configurazioni, decidi gli IP. Regola d'oro: **fuori dal pool DHCP del router**, altrimenti il router può assegnare lo stesso IP a un altro dispositivo. Controlla l'intervallo nell'interfaccia del router e adatta la tabella (qui assumo la rete `192.168.1.0/24` della lezione 4):

| Nome | IP | Ruolo | Quando esisterà |
|---|---|---|---|
| `hv.lab` | 192.168.1.50 | l'host Fedora (bridge `br0`) | già esiste |
| `bastion.lab` | 192.168.1.51 | VM di accesso e servizi di appoggio | Fase 2 |
| `storage.lab` | 192.168.1.55 | VM storage/NFS | Fase 2 |
| `master.lab` | 192.168.1.60 | nodo control plane Kubernetes | Fase 4 |
| `worker1.lab` | 192.168.1.61 | worker Kubernetes | Fase 4 |
| `worker2.lab` | 192.168.1.62 | worker Kubernetes | Fase 4 |

### 1. Osserva lo stato attuale del DNS sul tuo host

```bash
ls -l /etc/resolv.conf                 # link simbolico a /run/systemd/resolve/...
cat /etc/resolv.conf                   # nameserver 127.0.0.53
resolvectl status                      # DNS e domini per ogni interfaccia
grep ^hosts /etc/nsswitch.conf         # l'ordine delle fonti di risoluzione
sudo ss -lunp | grep ':53 '            # chi ascolta già sulla porta 53 (UDP)
```

Annota chi sta già sulla porta 53: dovrebbe essere `systemd-resolved` su `127.0.0.53` (e `127.0.0.54`). Ti serve per capire perché dnsmasq va configurato con attenzione.

### 2. Allenati con `dig` prima di costruire qualcosa

Installa gli strumenti, che su Fedora sono nel pacchetto `bind-utils`:

```bash
sudo dnf install -y bind-utils
```

Poi esplora:

```bash
dig example.com                        # leggi: status, ANSWER SECTION, TTL, Query time, SERVER
dig +short example.com                 # solo la risposta
dig example.com MX                     # un altro tipo di record
dig example.com NS                     # i server autoritativi
dig @1.1.1.1 example.com               # interroga un server specifico
dig +trace example.com                 # segui la risoluzione dalla radice, passo passo
dig -x 1.1.1.1                         # reverse lookup (PTR)
dig +noall +answer example.com         # output ridotto ma con TTL
```

Cosa osservare in una risposta di `dig`:

- **`status:`** → `NOERROR` (ok), `NXDOMAIN` (il nome non esiste), `SERVFAIL` (il server non è riuscito a rispondere).
- **`ANSWER SECTION`** → il record e il suo TTL.
- **`Query time`** e **`SERVER`** → quanto ha impiegato e chi ha risposto.

Ripeti due volte `dig example.com` e confronta il TTL e il `Query time`: la seconda volta il TTL è diminuito, perché stai leggendo una risposta dalla cache.

### 3. Installa dnsmasq

```bash
sudo dnf install -y dnsmasq
rpm -qc dnsmasq                        # elenca i suoi file di configurazione
ls /etc/dnsmasq.d/                     # qui metterai la tua configurazione
```

Su Fedora la configurazione principale (`/etc/dnsmasq.conf`) include i file in `/etc/dnsmasq.d/`: non toccare il file principale, aggiungi un file tuo.

**Il problema della porta 53.** Sulla porta 53 c'è già `systemd-resolved` (e, quando installerai libvirt nella Fase 2, anche il suo dnsmasq interno su `virbr0`). Se il tuo dnsmasq provasse ad ascoltare su *tutti* gli indirizzi, fallirebbe con un errore "address already in use". La soluzione è farlo ascoltare **solo sull'interfaccia `br0`** (`interface=br0`) e usare `bind-dynamic`: questa modalità fa legare dnsmasq agli indirizzi delle singole interfacce, convive con altri servizi sulla porta 53 e gestisce anche il caso in cui `br0` compaia dopo l'avvio (utile al boot).

### 4. Scrivi la configurazione del laboratorio

```bash
sudo nano /etc/dnsmasq.d/homelab.conf
```

Contenuto (adatta gli indirizzi alla tua tabella):

```ini
# ---------- Comportamento generale ----------
interface=br0              # ascolta solo sul bridge del lab
bind-dynamic               # convive con systemd-resolved e (poi) con libvirt
no-resolv                  # non leggere /etc/resolv.conf: upstream esplicito
server=1.1.1.1             # forwarder per tutto ciò che non è .lab
server=9.9.9.9
domain-needed              # non inoltrare nomi senza punto (es. "master")
bogus-priv                 # non inoltrare reverse lookup di reti private
cache-size=1000

# ---------- Dominio interno ----------
local=/lab/                # .lab è gestito SOLO da noi: mai inoltrato all'esterno
domain=lab
expand-hosts

# ---------- Record A (+ PTR creato in automatico) ----------
host-record=hv.lab,192.168.1.50
host-record=bastion.lab,192.168.1.51
host-record=storage.lab,192.168.1.55
host-record=master.lab,192.168.1.60
host-record=worker1.lab,192.168.1.61
host-record=worker2.lab,192.168.1.62

# ---------- Alias (CNAME) ----------
cname=registry.lab,bastion.lab
cname=git.lab,bastion.lab

# ---------- Wildcard: tutto *.apps.lab punta al cluster (servirà con l'Ingress) ----------
address=/apps.lab/192.168.1.60

# ---------- TXT e SRV di esempio ----------
txt-record=lab,"v=homelab1"
srv-host=_ssh._tcp.lab,bastion.lab,22

# ---------- Log delle query (togli quando non ti serve più) ----------
log-queries
```

Cosa fanno le direttive meno ovvie:

- **`local=/lab/`**: dice a dnsmasq "per `.lab` rispondi tu, non chiedere a nessuno". Un nome `.lab` che non esiste riceve subito `NXDOMAIN` invece di essere inoltrato a `1.1.1.1` (che non lo conosce e farebbe solo perdere tempo e rivelare i nomi interni).
- **`address=/apps.lab/IP`**: risponde con quell'IP per `apps.lab` **e per ogni suo sottodominio** (`grafana.apps.lab`, `app1.apps.lab`...). Quando installerai un Ingress controller ti permetterà di esporre servizi con nomi diversi senza toccare il DNS ogni volta.
- **`host-record`**: crea in un colpo solo il record A e il relativo PTR.

### 5. Valida, avvia, verifica

```bash
sudo dnsmasq --test                    # controlla la sintassi: deve dire "syntax check OK"
sudo systemctl enable --now dnsmasq
systemctl status dnsmasq
sudo ss -lunp | grep ':53 '            # ora vedi anche dnsmasq (su br0 e su lo)
sudo journalctl -u dnsmasq -n 30       # eventuali errori all'avvio
```

> **Abitudine da SRE**: valida **prima** di riavviare (`dnsmasq --test && systemctl restart dnsmasq`). Un riavvio con configurazione rotta lascia il servizio giù, e con esso la risoluzione dei nomi.

### 6. Apri la porta 53 nel firewall della zona `homelab`

Nella lezione 5 hai creato la zona `homelab` con target DROP: senza un permesso esplicito, i client della rete non raggiungono il tuo DNS.

```bash
sudo firewall-cmd --zone=homelab --add-service=dns            # prima solo runtime
# prova dal punto 7, poi:
sudo firewall-cmd --runtime-to-permanent
sudo firewall-cmd --zone=homelab --list-all                   # "dns" tra i servizi
```

### 7. Prova il tuo DNS

Dallo stesso host:

```bash
dig @192.168.1.50 master.lab +short          # 192.168.1.60
dig @192.168.1.50 worker1.lab +short
dig @192.168.1.50 example.com +short         # forwarding verso 1.1.1.1
dig @192.168.1.50 inesistente.lab            # status: NXDOMAIN, risposta immediata
```

**Da un altro dispositivo** (altro PC, telefono con app tipo "Net Analyzer", `nslookup`):

```bash
dig @192.168.1.50 master.lab +short
# oppure, senza dig:
nslookup master.lab 192.168.1.50
```

Ricorda la lezione 5: i test dallo stesso host passano dall'interfaccia `lo` e **non attraversano il firewall**. Solo il test da un altro dispositivo dimostra che la regola del punto 6 funziona davvero. Prova anche a rimuovere temporaneamente il servizio `dns` dalla zona (`--remove-service=dns`) e ripetere il test da fuori: otterrai un **timeout**, non un rifiuto. Poi rimettilo.

### 8. Fai usare il tuo DNS all'host stesso

Finora hai interrogato dnsmasq "a mano". Ora fai in modo che l'host lo usi in automatico, configurando la connessione `br0` (quella della lezione 4):

```bash
sudo nmcli connection modify br0 ipv4.dns 192.168.1.50 ipv4.dns-search lab
sudo nmcli connection up br0
resolvectl status br0                         # DNS Servers: 192.168.1.50, Search Domains: lab
```

> Attenzione: `connection up` riavvia brevemente la rete. Se sei da SSH, fallo da console locale.

Ora verifica con gli strumenti che passano da `nsswitch`/`resolved`, non con `dig`:

```bash
ping -c 2 master.lab                          # risponde "da 192.168.1.60"? Dipende dalla VM: non esiste ancora!
getent hosts master.lab                       # mostra solo la risoluzione, senza ping
resolvectl query master.lab                   # dice anche QUALE server e interfaccia hanno risposto
getent hosts master                           # funziona grazie al search domain "lab"
```

`ping` mostrerà il nome risolto ma non riceverà risposta (la VM non c'è ancora): quello che ti interessa è che la **risoluzione** funzioni (`PING master.lab (192.168.1.60)`).

Confronta ora i due livelli, è il cuore diagnostico della lezione:

```bash
dig master.lab +short                         # NB: dig usa 127.0.0.53 e non vede il search domain
dig @192.168.1.50 master.lab +short           # interroga direttamente dnsmasq
getent hosts master.lab                       # percorso reale delle applicazioni
```

### 9. Prova tutti i tipi di record

```bash
dig @192.168.1.50 -x 192.168.1.60 +short                  # PTR: master.lab.
dig @192.168.1.50 registry.lab                            # CNAME → bastion.lab → 192.168.1.51 (vedi la catena)
dig @192.168.1.50 grafana.apps.lab +short                 # wildcard: 192.168.1.60
dig @192.168.1.50 qualsiasi-cosa.apps.lab +short          # idem
dig @192.168.1.50 TXT lab +short                          # "v=homelab1"
dig @192.168.1.50 SRV _ssh._tcp.lab +short                # priorità, peso, porta 22, bastion.lab.
```

Nota la risposta del CNAME: contiene **due righe** (l'alias e il record A di destinazione). I client la seguono in modo trasparente.

### 10. Osserva cache e TTL

Guarda il journal in un secondo terminale mentre fai le query:

```bash
sudo journalctl -u dnsmasq -f
```

Dal primo terminale:

```bash
dig @192.168.1.50 example.com +noall +answer +stats       # prima: query "forwarded"
dig @192.168.1.50 example.com +noall +answer +stats       # poi: "cached", Query time ~0 msec, TTL ridotto
```

Nel journal vedrai la differenza tra `forwarded` e `cached`: è la cache di dnsmasq al lavoro.

Ora guarda il TTL dei tuoi record locali:

```bash
dig @192.168.1.50 master.lab +noall +answer
```

Per i record definiti localmente dnsmasq usa per default un TTL di **0** (il client non dovrebbe metterli in cache). Aggiungi in `homelab.conf`:

```ini
local-ttl=60
```

```bash
sudo dnsmasq --test && sudo systemctl restart dnsmasq
dig @192.168.1.50 master.lab +noall +answer               # il TTL ora è 60
resolvectl flush-caches                                    # svuota la cache dello stub dell'host
```

Domanda su cui ragionare: con TTL 60 quanto ci mettono i client a vedere un tuo cambio di IP? E con TTL 86400?

### 11. Esperimenti di rottura controllata

**A. Il DNS è un single point of failure.**

```bash
sudo systemctl stop dnsmasq
ping -c 1 master.lab                          # fallisce: "Name or service not known" o "Temporary failure..."
ping -c 1 192.168.1.1                         # funziona: la rete c'è, manca solo il DNS
curl -sS https://example.com                  # fallisce anche questo! L'host usa solo dnsmasq come DNS
sudo systemctl start dnsmasq
```

Hai appena riprodotto il motivo per cui in produzione ci sono **almeno due resolver**. Qui, per semplicità, l'host dipende da uno solo: è una scelta consapevole da laboratorio.

**B. Configurazione rotta.**

```bash
echo "questa-non-e-una-direttiva" | sudo tee -a /etc/dnsmasq.d/homelab.conf
sudo dnsmasq --test                           # segnala l'errore e la riga
sudo systemctl restart dnsmasq                # fallisce: il servizio resta giù
journalctl -u dnsmasq -n 10
# ripara togliendo l'ultima riga, poi:
sudo dnsmasq --test && sudo systemctl restart dnsmasq
```

**C. Tre modi diversi in cui il DNS "non risponde":**

```bash
dig @192.168.1.50 master.lab                          # NOERROR + risposta (tutto bene)
dig @192.168.1.50 inesistente.lab                     # NXDOMAIN: il server risponde "non esiste"
dig @192.168.1.99 master.lab +time=2 +tries=1         # timeout: nessun server DNS a quell'IP
```

| Segnale | Significato | Dove cercare |
|---|---|---|
| `NOERROR` con risposta | nome risolto | — |
| `NXDOMAIN` | il server risponde, ma il nome non esiste | record mancante, errore di battitura, dominio sbagliato |
| `SERVFAIL` | il server ha provato e non è riuscito (es. upstream irraggiungibile) | upstream, DNSSEC, configurazione |
| `timed out` / "no servers could be reached" | nessuna risposta | server spento, firewall (DROP), IP sbagliato |

Distinguere questi quattro casi è il primo passo di ogni diagnosi DNS.

### 12. Disattiva il log e documenta

Quando hai finito di studiare, togli `log-queries` (genera molto rumore e dati personali nel journal) e riavvia con la solita validazione. Poi salva la configurazione nel repo del progetto:

```bash
mkdir -p ~/homelab/dns
sudo cp /etc/dnsmasq.d/homelab.conf ~/homelab/dns/
sudo chown $USER: ~/homelab/dns/homelab.conf
```

Nel `NOTES.md` annota la **tabella degli IP** del punto 0: sarà il riferimento per le lezioni successive (le VM dovranno rispettarla).

## Bonus opzionale (30'): la stessa zona con BIND

Per vedere una zona "vera" con zone file, SOA e `named-checkzone`. **Ferma dnsmasq prima** (`sudo systemctl stop dnsmasq`): entrambi vorrebbero la porta 53 su `br0`.

```bash
sudo dnf install -y bind
sudo nano /etc/named.conf
```

Nelle opzioni fai ascoltare solo il bridge e consenti query dalla tua rete (adatta, e mantieni il resto del file di default):

```
options {
    listen-on port 53 { 127.0.0.1; 192.168.1.50; };
    allow-query { localhost; 192.168.1.0/24; };
    recursion yes;
    allow-recursion { localhost; 192.168.1.0/24; };
    forwarders { 1.1.1.1; 9.9.9.9; };
    // ...resto invariato...
};

zone "lab" IN {
    type master;
    file "lab.zone";
};
```

Crea il file di zona con il contenuto visto nella teoria:

```bash
sudo nano /var/named/lab.zone
sudo chown root:named /var/named/lab.zone
sudo restorecon -v /var/named/lab.zone        # etichetta SELinux corretta
sudo named-checkconf                           # valida named.conf
sudo named-checkzone lab /var/named/lab.zone   # valida la zona: deve dire "OK"
sudo systemctl enable --now named
dig @192.168.1.50 master.lab +short
```

Cose da osservare: il `serial` va **incrementato a ogni modifica** della zona (convenzione `AAAAMMGGNN`), altrimenti eventuali server secondari non si aggiornano; e il punto finale nei nomi assoluti. Alla fine ferma `named` e riattiva dnsmasq (`sudo systemctl disable --now named && sudo systemctl enable --now dnsmasq`).

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| dnsmasq non parte: `failed to create listening socket ... Address already in use` | Un altro processo (resolved, libvirt, un secondo dnsmasq) ha già la porta 53 su quell'indirizzo. Controlla con `ss -lunp \| grep :53` e restringi dnsmasq a `interface=br0` + `bind-dynamic` |
| `dig` funziona ma `ping`/`curl` no (o viceversa) | `dig` interroga direttamente un server, le app passano da `nsswitch` e `systemd-resolved`. Confronta con `getent hosts` e `resolvectl query` |
| Dall'host funziona, da un altro dispositivo va in timeout | Firewall: manca `dns` nella zona giusta, oppure il test locale passava da `lo` e non ha provato nulla |
| `master` (senza `.lab`) non si risolve | Manca il search domain sul client (`ipv4.dns-search lab`), oppure `domain-needed` blocca l'inoltro del nome senza punto e nessuno lo espande |
| Ho cambiato un record ma i client vedono ancora il vecchio IP | Cache: TTL non ancora scaduto sullo stub, su dnsmasq o sul client. `resolvectl flush-caches`, riavvio di dnsmasq, e ricorda di abbassare il TTL **prima** di una migrazione |
| Il nome `.lab` ci mette secondi a rispondere o "non esiste" dopo un'attesa | La query è stata inoltrata all'esterno: manca `local=/lab/` |
| Dopo il reboot dnsmasq è partito ma non risponde su `br0` | `br0` non era ancora pronta all'avvio: serve `bind-dynamic` (o un ordinamento esplicito con `After=network-online.target`) |
| Zone file BIND ignorato o con errori strani | Punto finale mancante nei FQDN, `serial` non incrementato, permessi/etichetta SELinux sbagliati (`restorecon`) |
| `Temporary failure in name resolution` su tutto | Il DNS configurato non risponde (es. dnsmasq fermo). Se l'host dipende da un unico resolver, perdi tutta la risoluzione |

## Perché è rilevante per l'SRE

Esiste un detto nel mondo operations: **"è sempre il DNS"**. Non è una battuta: molte interruzioni grosse, anche di aziende enormi, sono partite da un DNS rotto, da un TTL sbagliato o da una cache non invalidata. Quello che hai imparato qui ti serve in modo diretto:

- **Diagnosi per livelli**: `dig` (server) contro `getent`/`resolvectl` (client), e i quattro esiti (`NOERROR`, `NXDOMAIN`, `SERVFAIL`, timeout) ti restringono il problema in pochi secondi.
- **Kubernetes**: dentro il cluster il servizio di nomi è **CoreDNS**, e i nomi dei Service (`mio-servizio.namespace.svc.cluster.local`) sono record DNS. Anche i search domain e l'opzione `ndots` di `/etc/resolv.conf` dei pod, causa di tanti problemi di latenza, sono concetti che hai già incontrato qui.
- **Service discovery**: i record SRV sono la base di molti sistemi di discovery (etcd, Consul).
- **Migrazioni e rilasci**: la disciplina "abbassa il TTL, attendi, poi cambia" è una pratica standard prima di spostare un servizio.
- **Affidabilità**: aver visto che un solo resolver è un single point of failure ti prepara alle conversazioni su ridondanza e SLO delle dipendenze.
