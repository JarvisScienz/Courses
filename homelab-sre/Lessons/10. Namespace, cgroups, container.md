# Lezione 10 — Namespace, cgroups, immagini vs container: Docker sulla VM `app`

> **Dove siamo**: la Fase 2 è chiusa. Hai tre VM (`bastion` .51, `app` .52, `storage` .53), due reti (LAN su `br0` e `storage-net` isolata) e un accesso via `ProxyJump`. Da oggi inizia la **Fase 3 — Containerizzazione**. Installerai Docker su `app` e containerizzerai una piccola app Node. Ma prima smonti la "magia": un container **non è una mini-VM**, è un normale processo Linux con una vista limitata del sistema (namespace) e un tetto alle risorse (cgroups). Capirlo oggi ti servirà in modo diretto per `OOMKilled` e `CrashLoopBackOff` (lezione 18) e per i `resources.limits` di Kubernetes.

## Teoria (30-45')

### VM vs container: cosa cambia davvero

| | **VM** (lezioni 7-9) | **Container** |
|---|---|---|
| Kernel | Ne ha uno **proprio** (guest) | **Condivide** quello dell'host |
| Isolamento | Hardware virtuale (KVM) | Namespace + cgroups + capability + seccomp |
| Avvio | Decine di secondi (boot completo) | Millisecondi (è un `fork`/`exec`) |
| Peso | GB (disco intero) | MB (solo i file dell'app e delle sue librerie) |
| Confine di sicurezza | Forte | Più debole: un bug del kernel è un problema per tutti |
| Cosa contiene | Un OS completo | Un processo e il suo filesystem |

Corollario che frega tutti: **non puoi eseguire un container Linux con un kernel diverso** da quello dell'host. Un container "Ubuntu" su Fedora usa il kernel Fedora; ha solo i file userland di Ubuntu. Verificherai la cosa col comando `uname -r`.

### I namespace: cosa il processo *vede*

Un namespace è una vista privata di una risorsa globale del kernel. Il processo dentro il container crede di essere solo al mondo.

| Namespace | Isola | Effetto visibile |
|---|---|---|
| `pid` | Albero dei processi | Dentro il container l'app è **PID 1**; i processi dell'host non si vedono |
| `net` | Interfacce, rotte, porte, regole nftables | Il container ha la sua `eth0`, la sua tabella di routing, il suo `localhost` |
| `mnt` | Punti di mount | Il container ha il suo `/`, costruito dall'immagine |
| `uts` | Hostname | `hostname` dentro ≠ `hostname` fuori |
| `ipc` | Code di messaggi, memoria condivisa | Niente IPC condiviso con l'host |
| `user` | UID/GID | `root` nel container può essere un utente senza privilegi sull'host (se abilitato) |
| `cgroup` | Vista della gerarchia dei cgroup | Il container non vede i limiti degli altri |

Li vedi in `/proc/<pid>/ns/`: ogni file è un link con un numero di inode. **Due processi con lo stesso inode condividono quel namespace.** Questo è l'unico modo affidabile per sapere "sono dentro o fuori?".

Hai già incontrato i namespace `net` senza saperlo: sono quello che libvirt non usa per le VM (le VM hanno un kernel proprio), ma che Docker usa per dare a ogni container la sua pila di rete, collegata all'host con una coppia **veth**, un cavo virtuale con un capo nel container e l'altro agganciato a un bridge (`docker0`). È lo stesso schema bridge ↔ porta `vnetN` della lezione 9, con un nome diverso.

### I cgroups: cosa il processo può *consumare*

I **control groups** limitano e contabilizzano CPU, memoria, I/O e numero di processi di un gruppo di processi. Su Fedora si usa **cgroup v2**: una gerarchia unica montata in `/sys/fs/cgroup`, gestita da systemd (quindi ritrovi la lezione 1: ogni servizio e ogni container è uno *slice/scope* con i suoi limiti).

File che leggerai oggi:

| File | Significato |
|---|---|
| `memory.max` | Tetto di RAM. Superato → il kernel invoca l'**OOM killer** nel gruppo |
| `memory.current` | RAM usata ora |
| `memory.events` | Contatori, tra cui `oom_kill` |
| `cpu.max` | Quota CPU, formato `quota periodo` (es. `50000 100000` = mezza CPU) |
| `pids.max` | Numero massimo di processi (difesa contro le fork bomb) |

Nota la differenza di comportamento, perché è una domanda classica da colloquio:

- **CPU oltre il limite → throttling.** Il processo rallenta, non muore.
- **Memoria oltre il limite → OOM kill.** Il processo muore (exit code **137** = 128 + SIGKILL).

### Immagine vs container

- **Immagine**: un insieme **immutabile e a strati** (layer) di file, più metadati (comando di default, variabili, porte). È una ricetta + gli ingredienti. Si identifica con un *digest* `sha256:...`.
- **Container**: un'**istanza in esecuzione** (o fermata) di un'immagine: i layer dell'immagine in sola lettura, più un sottile **layer scrivibile** in cima, più i namespace e i cgroups.
- **Tag** (`node:22-alpine`): un'etichetta **mobile** che punta a un digest. `latest` oggi non è `latest` domani: in produzione si fissano versione o digest.
- Cancellare un container butta via il suo layer scrivibile: **i dati scritti dentro il container si perdono**. Per quelli servono i volumi (lezione 12).

Le immagini sono impacchettate nel formato **OCI**: Docker, Podman, containerd e Kubernetes parlano tutti la stessa lingua. Quando in lezione 13 Kubernetes non userà più Docker ma `containerd`, le tue immagini funzioneranno senza modifiche.

### L'architettura di Docker

```
 docker (CLI)  ──REST su /var/run/docker.sock──▶  dockerd (demone)
                                                      │
                                                      ▼
                                                  containerd   (gestisce immagini e ciclo di vita)
                                                      │
                                                      ▼
                                                  runc         (crea namespace + cgroups, fa exec)
                                                      │
                                                      ▼
                                           il tuo processo (PID 1 del container)
```

- La CLI è solo un client. Chi lavora è **`dockerd`**, che gira come root.
- **Chi può parlare con `/var/run/docker.sock` è, di fatto, root sull'host.** Può montare `/` in un container e farci quello che vuole. Aggiungere un utente al gruppo `docker` equivale a dargli `sudo` senza password: ricordati della lezione 2 e decidi consapevolmente.
- **Podman** (il default Red Hat/Fedora) fa la stessa cosa senza demone e senza root. Qui usi Docker perché il percorso e la maggior parte della documentazione che incontrerai (Compose, CI, tutorial) lo danno per scontato.

## Pratica (75-90')

Lavori sulla VM `app` (da cui ssh passa dal bastion se hai configurato `~/.ssh/config` come in lezione 9).

### 0. Stato di partenza e snapshot

Dall'host:

```bash
virsh list --all                         # bastion, app, storage accese
virsh snapshot-create-as app pre-docker "Prima di installare Docker" --atomic
virsh snapshot-list app
```

Lo snapshot (lezione 8) è la tua rete di sicurezza: se Docker rompe la rete della VM, torni indietro con `virsh snapshot-revert app pre-docker`.

Poi dentro `app`:

```bash
ssh app.lab
cat /etc/fedora-release
uname -r
stat -fc %T /sys/fs/cgroup               # cgroup2fs  → cgroup v2
ip -br addr; ip route
sudo nft list ruleset | wc -l            # annota il numero: lo riconfronti dopo
sudo firewall-cmd --get-active-zones
```

Salva l'output di `ip route` e `nft list ruleset | wc -l`: dopo l'installazione Docker aggiungerà un bridge e delle regole, e vuoi vedere **cosa** è cambiato.

### 1. Installa Docker Engine

Dal repository ufficiale Docker (i pacchetti di Fedora si chiamano `moby-engine` e sono vecchi):

```bash
sudo dnf -y install dnf-plugins-core
sudo dnf config-manager addrepo --from-repofile=https://download.docker.com/linux/fedora/docker-ce.repo
sudo dnf -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
systemctl status docker --no-pager
docker version
sudo docker run --rm hello-world
```

Se `dnf config-manager addrepo` non esiste (dnf4 su una Fedora vecchia), usa la sintassi alternativa: `sudo dnf config-manager --add-repo https://download.docker.com/linux/fedora/docker-ce.repo`.

Cosa è successo? Leggi il flusso nell'output di `hello-world`: la CLI ha contattato il demone, il demone ha **scaricato** l'immagine da Docker Hub, ha creato un container, ha eseguito il binario e ha stampato lo stdout.

> **Il gruppo `docker`.** Per non digitare `sudo` ogni volta puoi fare `sudo usermod -aG docker $USER`. Ma leggi la teoria: è root equivalente. In un homelab è una scelta accettabile; **annotala in `NOTES.md` come rischio accettato**, non come comodità innocua. In questa lezione i comandi usano `docker` senza `sudo`: dopo `usermod` fai logout/login (o `newgrp docker`).

### 2. Cosa è cambiato sul sistema

```bash
ip -br addr show docker0                 # nuovo bridge, tipicamente 172.17.0.1/16
ip -br link show type bridge
ip route                                 # nuova rotta 172.17.0.0/16 dev docker0
sudo nft list ruleset | wc -l            # molte più righe
sudo firewall-cmd --get-active-zones     # compare la zona "docker"?
sysctl net.ipv4.ip_forward
```

Collega i punti con le lezioni 4, 5 e 9:

- `docker0` è un bridge Linux come `br0`: una porta per ogni container (la `vethXXXX`).
- Docker ha attivato `ip_forward`, perché instrada tra `docker0` e `lan0`.
- Docker ha creato regole di **masquerade** per `172.17.0.0/16`: è il NAT che hai visto cambiando `storage-net` in lezione 9. Un container esce su internet con l'IP della VM.
- Su Fedora Docker convive con `firewalld` creando la sua zona `docker`: se un giorno i container "non escono" dopo un `firewall-cmd --reload`, il sospetto è qui.

Controlla un possibile **conflitto di subnet**: `172.17.0.0/16` non deve sovrapporsi a reti che usi (la tua LAN è 192.168.1.0/24 e `storage-net` 10.10.10.0/24, quindi sei a posto). In reti aziendali con VPN questo è un guasto classico: Docker sceglie un range che collide con una rete interna.

### 3. Un container è un processo: toccarlo con mano

Avvia un container e osservalo da **fuori**:

```bash
docker run -d --name sleeper alpine:3.20 sleep 3600
docker ps
docker top sleeper                       # il processo come lo vede l'host
ps -ef | grep "sleep 3600" | grep -v grep
```

Il `sleep 3600` che gira dentro il container è visibile con il suo PID **host** (diverso da 1). Ecco la prova: è un processo normale. Ora da **dentro**:

```bash
docker exec sleeper ps                   # lì sleep è PID 1
docker exec sleeper hostname
docker exec sleeper uname -r             # il kernel è quello della VM!
uname -r
```

Il kernel è lo stesso: lo avevi letto nella teoria, ora l'hai visto.

### 4. Namespace: confronta gli inode

```bash
PID=$(docker inspect -f '{{.State.Pid}}' sleeper)
echo "PID host del container: $PID"
sudo ls -l /proc/$PID/ns/
sudo ls -l /proc/self/ns/
```

Confronta le due liste: gli inode di `pid`, `net`, `mnt`, `uts`, `ipc` sono **diversi** (namespace separati). Quello di `user` è probabilmente **uguale** (di default Docker non usa user namespace: il root del container è il root dell'host, con capability ridotte). Annotalo: è una scelta di sicurezza che si può cambiare con `userns-remap`, e Kubernetes la sta introducendo gradualmente.

Entra **nel namespace di rete** del container dall'host, senza `docker exec`:

```bash
sudo nsenter -t $PID -n ip -br addr      # la eth0 del container, vista dall'host
sudo nsenter -t $PID -n ip route
ip -br link | grep veth                  # il capo "host" del cavo
bridge link show master docker0          # la veth è una porta del bridge docker0
```

È il filo che lega questa lezione alla 9: `eth0@ifNN` nel container ↔ `vethXXXX` sull'host ↔ porta di `docker0`. Per provare che i namespace sono creabili senza Docker:

```bash
sudo unshare --pid --fork --mount-proc --uts bash
hostname isolato; hostname               # cambia solo qui dentro
ps -ef                                   # vedi solo i processi del namespace
exit
hostname                                 # fuori è rimasto quello vero
```

Hai appena fatto, in tre righe, la parte "isolamento" di un container.

### 5. cgroups: metti un tetto alla memoria e osserva l'OOM

```bash
docker run -d --name memhog --memory 64m --memory-swap 64m --cpus 0.5 alpine:3.20 sleep 3600
CID=$(docker inspect -f '{{.Id}}' memhog)
CG=/sys/fs/cgroup/system.slice/docker-$CID.scope
cat $CG/memory.max                       # 67108864 = 64 MiB
cat $CG/cpu.max                          # 50000 100000 = mezza CPU
cat $CG/pids.max
cat $CG/memory.current
```

Se il percorso non esiste, il tuo Docker usa il driver cgroup `cgroupfs` invece di `systemd` (`docker info | grep -i cgroup`). Trovi comunque il percorso con `cat /proc/$(docker inspect -f '{{.State.Pid}}' memhog)/cgroup`.

Ora **supera il limite**. Alpine non ha strumenti di stress, ma una riga di `sh` basta:

```bash
docker exec memhog sh -c 'x=; while true; do x="$x$(head -c 1000000 /dev/zero | tr "\0" a)"; done'
echo "exit code: $?"                      # 137 = SIGKILL, ucciso dall'OOM killer
docker inspect -f '{{.State.OOMKilled}}' memhog
cat $CG/memory.events                    # oom_kill ≥ 1
sudo dmesg | grep -i "memory cgroup out of memory" | tail -3
```

Tre cose da fissare: l'**exit code 137**, il flag **`OOMKilled: true`**, e la riga nel `dmesg`. Quando in lezione 18 Kubernetes ti mostrerà `Reason: OOMKilled`, `Exit Code: 137` in `kubectl describe pod`, sarà esattamente questo.

Ora la CPU, che si comporta **diversamente**:

```bash
docker run -d --name cpuhog --cpus 0.25 alpine:3.20 sh -c 'while :; do :; done'
sleep 5
docker stats --no-stream cpuhog          # ~25% e non 100%: throttling
cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' cpuhog).scope/cpu.stat | grep -E "nr_throttled|throttled_usec"
```

Il processo non è morto: è stato **rallentato**. `nr_throttled` cresce. Conseguenza reale: un'app con limite CPU troppo basso non crasha, **diventa lenta**, e la latenza aumenta in modo misterioso. È uno dei guasti più subdoli in produzione e lo rivedrai nella Fase 5 (metrica `container_cpu_cfs_throttled_periods_total`).

Pulizia:

```bash
docker rm -f sleeper memhog cpuhog
```

### 6. Immagini e layer: leggi come sono fatte

```bash
docker pull node:22-alpine
docker pull node:22
docker images
docker history node:22-alpine
docker image inspect node:22-alpine --format '{{.Id}} {{len .RootFS.Layers}} layer'
```

Confronta i **pesi**: `node:22` (Debian) è circa 1 GB, `node:22-alpine` circa 150-200 MB. Alpine usa `musl` invece di `glibc` e `apk` invece di `apt`: più piccola e con superficie d'attacco minore, ma qualche modulo nativo di npm può dare problemi. È una scelta, non un default universale.

Vedi dove vivono i layer sull'host:

```bash
docker info | grep -E "Storage Driver|Docker Root Dir"      # overlayfs, /var/lib/docker
sudo du -sh /var/lib/docker
```

E come **overlayfs** li compone per un container:

```bash
docker run -d --name ov alpine:3.20 sleep 3600
docker inspect -f '{{.GraphDriver.Data.LowerDir}}' ov | tr ':' '\n'      # layer read-only
docker inspect -f '{{.GraphDriver.Data.UpperDir}}' ov                    # layer scrivibile
docker exec ov sh -c 'echo ciao > /nuovo-file'
sudo ls $(docker inspect -f '{{.GraphDriver.Data.UpperDir}}' ov)         # c'è "nuovo-file"
docker diff ov                                                           # A /nuovo-file
docker rm -f ov
```

Il file è finito **solo** nel layer scrivibile (`UpperDir`); l'immagine è intatta. Rimosso il container, è sparito: ecco perché i dati vanno nei volumi.

### 7. L'app da containerizzare

Usa **una tua app Node/React esistente**. Se non ne scegli una, parti da questa API minimale, che ti basta per tutto il resto del percorso (la riprenderai nelle lezioni 11, 12 e 15):

```bash
mkdir -p ~/homelab/app-demo && cd ~/homelab/app-demo
cat > package.json <<'EOF'
{
  "name": "app-demo",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": { "start": "node server.js" }
}
EOF

cat > server.js <<'EOF'
const http = require('http');
const os = require('os');

const PORT = process.env.PORT || 3000;
let requests = 0;

const server = http.createServer((req, res) => {
  if (req.url === '/healthz') {
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    return res.end('ok\n');
  }
  requests += 1;
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({
    host: os.hostname(),
    pid: process.pid,
    requests,
    uptime_s: Math.round(process.uptime()),
  }) + '\n');
});

server.listen(PORT, '0.0.0.0', () => console.log(`listening on ${PORT}`));

process.on('SIGTERM', () => {
  console.log('SIGTERM ricevuto, chiudo');
  server.close(() => process.exit(0));
});
EOF
```

Il gestore di `SIGTERM` non è decorativo: lo capirai al punto 10.

### 8. Il primo Dockerfile

```bash
cat > Dockerfile <<'EOF'
FROM node:22-alpine
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev
COPY server.js ./
EXPOSE 3000
CMD ["node", "server.js"]
EOF

cat > .dockerignore <<'EOF'
node_modules
npm-debug.log
.git
.env
Dockerfile
EOF
```

Costruisci ed esegui:

```bash
docker build -t app-demo:0.1 .
docker images app-demo
docker run -d --name demo -p 8080:3000 app-demo:0.1
docker logs demo
curl -s localhost:8080
curl -s localhost:8080
```

Dall'**host Fedora** (non dalla VM) raggiungi l'app sull'IP di `app`:

```bash
curl -s http://app.lab:8080/
```

Funziona perché `-p 8080:3000` aggiunge una regola **DNAT** nftables: la porta 8080 della VM viene inoltrata a `172.17.0.2:3000`. Verificalo:

```bash
sudo nft list ruleset | grep -B2 -A2 "dport 8080"
docker port demo
```

Se dall'host non risponde, controlla il **firewall del guest** (lezione 5): Docker aggiunge le sue regole, ma se hai `firewalld` con zona restrittiva su `lan0` potresti dover aprire la porta con `sudo firewall-cmd --add-port=8080/tcp`.

> **Differenza tra `EXPOSE` e `-p`.** `EXPOSE` è solo documentazione (metadato dell'immagine). Pubblicare una porta è una scelta di chi **esegue** il container (`-p`). Ritroverai lo stesso schema in Kubernetes: `containerPort` vs `Service`.

> **Attenzione: `-p 8080:3000` ascolta su `0.0.0.0`.** Docker pubblica la porta su **tutte** le interfacce, comprese quelle su `storage-net`, e *scavalca* parte delle regole del firewall dell'host. Per esporla solo dove serve: `-p 192.168.1.52:8080:3000`.

### 9. Ispezione: cosa c'è dentro, chi lo esegue

```bash
docker exec demo whoami                  # root!
docker exec demo id
docker exec demo ps
docker inspect demo --format '{{json .Config.Env}}'
docker inspect demo --format '{{.NetworkSettings.IPAddress}}'
docker stats --no-stream demo
```

Il processo gira come **root** dentro il container. Per un'app Node non serve: la immagine ufficiale include un utente `node` (UID 1000). Aggiungilo e ricostruisci:

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY --chown=node:node package.json ./
RUN npm install --omit=dev
COPY --chown=node:node server.js ./
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

```bash
docker build -t app-demo:0.2 .
docker rm -f demo
docker run -d --name demo -p 8080:3000 app-demo:0.2
docker exec demo whoami                  # node
```

Gira come `node` (UID 1000) e questo stesso UID lo vedi dall'host con `ps -o user,pid,cmd -C node`. È la prima, più economica misura di hardening: se qualcuno sfrutta una vulnerabilità nell'app, non ha subito root nel container.

### 10. Ciclo di vita e segnali: `docker stop` e PID 1

```bash
time docker stop demo                    # molto veloce: l'app gestisce SIGTERM
docker logs demo | tail -3               # "SIGTERM ricevuto, chiudo"
docker start demo
```

Ora una prova di contrasto: avvia lo stesso programma con la "forma shell" del `CMD`, che mette una shell come PID 1:

```bash
docker run -d --name demo-sh --entrypoint /bin/sh app-demo:0.2 -c "node server.js"
time docker stop demo-sh                 # ~10 secondi, poi SIGKILL
docker logs demo-sh | tail -3            # NIENTE "SIGTERM ricevuto"
docker rm demo-sh
```

La `sh` è PID 1 e non inoltra `SIGTERM` al figlio: il demone aspetta **10 secondi** (il timeout) e poi invia `SIGKILL`. L'app non ha potuto chiudere le connessioni. È il motivo per cui si usa sempre la **forma exec** `CMD ["node", "server.js"]` (con le parentesi quadre) e, se serve un init vero, `--init` (tini). In Kubernetes, `terminationGracePeriodSeconds` (30 s di default) fa la stessa cosa: un'app che ignora `SIGTERM` allunga ogni rolling update.

### 11. Politiche di riavvio e crash

```bash
docker rm -f demo
docker run -d --name demo -p 8080:3000 --restart unless-stopped app-demo:0.2
docker kill demo                         # simula un crash (SIGKILL)
sleep 2; docker ps                       # il demone l'ha riavviato
docker inspect -f '{{.RestartCount}}' demo
```

Verifica la persistenza al reboot: `sudo reboot` sulla VM, poi `ssh app.lab docker ps`. Il container riparte perché `dockerd` è abilitato in systemd (`systemctl is-enabled docker`) **e** il container ha una `restart policy`. Il comportamento è il precursore di quello che Kubernetes farà con i Pod, includendo il famoso **backoff esponenziale** che vedrai come `CrashLoopBackOff`.

Provocalo ora, a piccola scala:

```bash
docker run -d --name crasher --restart on-failure:5 alpine:3.20 sh -c 'echo parto; exit 1'
sleep 20
docker logs crasher
docker inspect -f '{{.RestartCount}} {{.State.Status}} {{.State.ExitCode}}' crasher
docker rm -f crasher
```

### 12. Il cleanup: Docker occupa spazio

```bash
docker system df
docker ps -a
docker image prune -f                    # immagini "dangling"
docker system df -v | head -20
```

`/var/lib/docker` è sul disco della VM: su una VM da 20 GB, un `docker build` ripetuto la riempie. È un guasto reale e comune ("no space left on device" sul nodo Kubernetes). Aggiungi il controllo a `NOTES.md`, con il comando per risolvere: `docker system prune -af --volumes` (**attenzione**: cancella anche i volumi inutilizzati, quindi mai su un host con dati).

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| `permission denied while trying to connect to the Docker daemon socket` | L'utente non è nel gruppo `docker`, o la sessione non è stata riaperta dopo `usermod -aG` |
| `Cannot connect to the Docker daemon at unix:///var/run/docker.sock` | `dockerd` non avviato: `systemctl status docker`, `journalctl -u docker -n 50` |
| Il container non raggiunge internet | `ip_forward` a 0, o la zona `docker` di firewalld non ha il masquerade; DNS: controlla `docker exec <c> cat /etc/resolv.conf` |
| Dall'host `curl app.lab:8080` va in timeout | Porta non pubblicata (`docker port`), firewall del guest, o l'app ascolta su `127.0.0.1` invece che su `0.0.0.0` dentro il container |
| L'app si avvia ma la porta pubblicata non risponde | Il processo dentro è in ascolto su `localhost`: un container ha **il suo** `localhost`, non quello dell'host. Usa `0.0.0.0` |
| Exit code **137** | `SIGKILL`: OOM killer (`docker inspect` → `OOMKilled`), oppure `docker stop` oltre il timeout, oppure `docker kill` |
| Exit code **143** | `SIGTERM` gestito e uscita pulita da segnale: normale in uno stop |
| Exit code **1** / **127** / **126** | Errore applicativo / comando non trovato / comando non eseguibile (permessi, `CMD` sbagliato) |
| `docker stop` impiega sempre 10 s | L'app non gestisce `SIGTERM`, o la forma `shell` del `CMD`/`ENTRYPOINT` mette una `sh` come PID 1 |
| Il build è lento a ogni modifica | `COPY . .` prima di `npm install`: la cache dei layer si invalida a ogni cambio. Copia prima `package.json`, poi installa, poi copia il codice (lezione 11) |
| `exec format error` | Immagine per un'architettura diversa (es. ARM su x86): `docker image inspect --format '{{.Architecture}}'` |
| `no space left on device` | `/var/lib/docker` pieno: `docker system df`, poi `docker system prune` |
| I container non partono dopo un `firewall-cmd --reload` | Il reload ha rimosso le regole di Docker; riavvia `docker` (`systemctl restart docker`) |
| `address range conflicts` / rotte strane dopo aver installato Docker | `172.17.0.0/16` si sovrappone a una rete che già usi: configura `bip` in `/etc/docker/daemon.json` |
| `unshare`/`nsenter` dicono `Operation not permitted` | Serve `sudo` (i namespace richiedono `CAP_SYS_ADMIN`) |
| Il file `/sys/fs/cgroup/system.slice/docker-<id>.scope` non esiste | Driver cgroup `cgroupfs` anziché `systemd`: leggi il percorso reale da `/proc/<pid>/cgroup` |

## Perché è rilevante per l'SRE

- **Un container è un processo.** Tutto ciò che sai fare con i processi (`ps`, `strace`, `nsenter`, `/proc`, `journalctl`) vale per i container. Quando `docker exec` non funziona o il container non ha neanche una shell (immagini *distroless*), `nsenter` dall'host è la via d'uscita che sai già percorrere.
- **Limiti di memoria e di CPU sono un contratto.** Memoria: superi → muori (137). CPU: superi → rallenti (throttling). Capire la differenza ti permette di scegliere `requests` e `limits` di Kubernetes (lezione 15) senza tirare a indovinare, e di riconoscere la latenza "inspiegabile" dovuta al throttling.
- **Immutabilità.** L'immagine è un artefatto versionato; il container è un'istanza usa-e-getta. Questo è ciò che rende possibili rollback, rolling update e scaling orizzontale: la stessa logica che userai nelle pipeline (lezione 26).
- **Segnali e ciclo di vita.** PID 1, `SIGTERM`, grace period, `restart policy`: sono il fondamento dei deploy senza downtime. Un'app che non muore in modo pulito causa errori a ogni rilascio, anche se "funziona".
- **Sicurezza di base.** Utente non root, `docker.sock` = root, porte pubblicate su `0.0.0.0`, tag mobili: sono quattro decisioni prese in questa lezione che corrispondono a voci di qualsiasi checklist di hardening.
- **Spazio disco.** Un nodo con `/var/lib/docker` pieno è un incidente classico. Averlo incontrato oggi significa riconoscerlo domani.
