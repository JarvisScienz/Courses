# Lezione 3 — Partizionamento, LVM, filesystem

> **Nota di sicurezza**: in questa lezione lavorerai su **immagini disco virtuali** (file `.img`), non su dischi fisici reali. È il modo corretto di fare pratica su LVM senza rischiare i tuoi dati: puoi rompere tutto e ricominciare semplicemente cancellando il file immagine.

## Teoria (45')

### Livelli di astrazione: disco → partizione → LVM → filesystem

Prima di tutto, la gerarchia concettuale, perché è facile perdersi tra i livelli:

```
Disco fisico (/dev/sdb)
  └─ Partizione (/dev/sdb1)
       └─ Physical Volume (PV)      ← LVM inizia qui
            └─ Volume Group (VG)     ← "pool" di spazio condiviso
                 └─ Logical Volume (LV)   ← quello che effettivamente monti
                      └─ Filesystem (ext4, xfs, ...)
```

Senza LVM, una partizione ha una dimensione fissa: se il disco si riempie, devi ripartizionare (doloroso, spesso richiede un riavvio o un backup/restore). Con LVM, lo spazio è un pool flessibile che puoi ridistribuire tra volumi logici **senza smontare né riavviare**, nella maggior parte dei casi.

### Partizionamento classico

Gli strumenti principali sono `fdisk` (tabelle MBR, più vecchio) e `parted`/`gdisk` (supportano anche GPT, necessario per dischi >2TB o UEFI).

```bash
sudo fdisk -l                 # elenca dischi e partizioni
sudo fdisk /dev/sdb            # entra in modalità interattiva su un disco
```

Da homelab userai quasi sempre immagini disco (vedi sezione pratica), ma il comando è identico anche su hardware reale — è uno dei motivi per cui vale la pena impararlo bene qui, senza il rischio di un disco vero.

### LVM: i tre livelli

1. **Physical Volume (PV)**: una partizione (o un intero disco) "marcata" per essere usata da LVM.
   ```bash
   sudo pvcreate /dev/sdb1
   sudo pvdisplay
   ```
2. **Volume Group (VG)**: un pool che raggruppa uno o più PV. È qui che vive lo spazio "libero" da assegnare.
   ```bash
   sudo vgcreate vg_homelab /dev/sdb1
   sudo vgdisplay
   ```
3. **Logical Volume (LV)**: una "partizione virtuale" ritagliata dal VG. È quello che effettivamente formatti e monti.
   ```bash
   sudo lvcreate -L 5G -n lv_dati vg_homelab
   sudo lvdisplay
   ```

Il vantaggio pratico: se `lv_dati` si riempie e nel VG c'è ancora spazio libero, puoi estenderlo **a caldo** (senza smontare, nella maggior parte dei casi con ext4/xfs):

```bash
sudo lvextend -L +2G /dev/vg_homelab/lv_dati
sudo resize2fs /dev/vg_homelab/lv_dati        # per ext4
# oppure
sudo xfs_growfs /mount/point                   # per xfs (attenzione: si monta il mount point, non il device!)
```

### ext4 vs xfs: differenze che contano davvero

| Aspetto | ext4 | xfs |
|---|---|---|
| Resize a caldo (crescita) | Sì | Sì |
| Resize a caldo (riduzione) | Sì (da smontato) | **No** — xfs non supporta il restringimento, mai |
| Journaling | Sì | Sì (più efficiente su file grandi) |
| Performance su tanti file piccoli | Buona | Ottima su file grandi, meno ottimale su moltissimi file piccoli senza tuning |
| Default su | Molte distro storiche | **Fedora e RHEL/CentOS dal 2014 in poi** |
| Caso d'uso tipico | Uso generico, VM, dischi che potrebbero dover restringersi | Storage per database, file di log di grandi dimensioni, dove serve solo crescere |

Il punto che sorprende di più chi arriva da altri sistemi: **xfs non si può mai rimpicciolire**, nemmeno smontato — se sbagli le dimensioni iniziali, l'unica strada è ricreare il filesystem e ripristinare i dati da backup. È una scelta di design (semplicità e performance), non un limite temporaneo. Questo influenza le decisioni di provisioning: con xfs conviene partire più stretti e far crescere, mai il contrario.

## Pratica (75-90')

### 1. Crea un'immagine disco virtuale invece di usare un disco vero

```bash
mkdir -p ~/homelab/disks
dd if=/dev/zero of=~/homelab/disks/disco1.img bs=1M count=2048   # 2GB
dd if=/dev/zero of=~/homelab/disks/disco2.img bs=1M count=2048   # un secondo disco, ti servirà dopo
```

Collegala come dispositivo a blocchi tramite loop device:

```bash
sudo losetup -fP ~/homelab/disks/disco1.img
losetup -a                       # trova il nome assegnato, es. /dev/loop0
```

Da qui in poi tratta `/dev/loop0` esattamente come tratteresti `/dev/sdb`.

### 2. Crea PV, VG, LV

```bash
sudo pvcreate /dev/loop0
sudo vgcreate vg_homelab /dev/loop0
sudo lvcreate -L 1G -n lv_ext4 vg_homelab
sudo lvcreate -L 500M -n lv_xfs vg_homelab

sudo vgdisplay vg_homelab       # nota "Free PE / Size" — quanto spazio resta nel pool
```

### 3. Formatta e monta i due volumi con filesystem diversi

```bash
sudo mkfs.ext4 /dev/vg_homelab/lv_ext4
sudo mkfs.xfs /dev/vg_homelab/lv_xfs

sudo mkdir -p /mnt/test-ext4 /mnt/test-xfs
sudo mount /dev/vg_homelab/lv_ext4 /mnt/test-ext4
sudo mount /dev/vg_homelab/lv_xfs /mnt/test-xfs

df -hT /mnt/test-ext4 /mnt/test-xfs    # verifica tipo filesystem e spazio
```

### 4. Genera un po' di dati e prova il resize a caldo

```bash
sudo dd if=/dev/zero of=/mnt/test-ext4/riempimento bs=1M count=800
df -h /mnt/test-ext4      # quasi pieno
```

Estendi il volume LVM e poi il filesystem sopra, **senza smontare**:

```bash
sudo lvextend -L +500M /dev/vg_homelab/lv_ext4
sudo resize2fs /dev/vg_homelab/lv_ext4
df -h /mnt/test-ext4      # ora ha più spazio, il file esistente è ancora lì
```

Fai lo stesso su xfs (nota la sintassi diversa: si passa il mount point, non il device):

```bash
sudo lvextend -L +200M /dev/vg_homelab/lv_xfs
sudo xfs_growfs /mnt/test-xfs
```

### 5. Aggiungi un secondo PV al VG (simula l'aggiunta di un disco fisico)

```bash
sudo losetup -fP ~/homelab/disks/disco2.img
losetup -a                                  # es. /dev/loop1
sudo pvcreate /dev/loop1
sudo vgextend vg_homelab /dev/loop1
sudo vgdisplay vg_homelab                   # ora il pool ha più spazio libero
```

Questo è esattamente lo scenario reale "il server sta finendo lo spazio, aggiungiamo un disco" — con LVM non serve spostare dati, basta estendere il pool.

### 6. Prova (e osserva il fallimento) del restringimento su xfs

```bash
sudo umount /mnt/test-xfs
sudo lvreduce -L 300M /dev/vg_homelab/lv_xfs
# ERRORE: xfs non supporta la riduzione. Osserva il messaggio d'errore.
```

Confrontalo con ext4, dove invece funziona (da smontato):

```bash
sudo umount /mnt/test-ext4
sudo e2fsck -f /dev/vg_homelab/lv_ext4         # obbligatorio prima di ridurre
sudo resize2fs /dev/vg_homelab/lv_ext4 900M
sudo lvreduce -L 900M /dev/vg_homelab/lv_ext4
```

> **Attenzione**: con ext4 l'ordine è invertito rispetto all'estensione — prima riduci il filesystem, *poi* il volume LVM. Se lo fai al contrario rischi di troncare dati ancora referenziati dal filesystem.

### 7. Pulizia (per rifare l'esercizio da zero se vuoi)

```bash
sudo umount /mnt/test-ext4 /mnt/test-xfs 2>/dev/null
sudo vgremove vg_homelab
sudo pvremove /dev/loop0 /dev/loop1
sudo losetup -d /dev/loop0
sudo losetup -d /dev/loop1
rm ~/homelab/disks/disco1.img ~/homelab/disks/disco2.img
```

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| `Device or resource busy` su `losetup -d` | Il loop device è ancora montato o ha un LV attivo sopra — smonta e fai `vgchange -an` prima |
| `resize2fs` non vede lo spazio esteso | Hai esteso il PV/VG ma dimenticato `lvextend` sul LV specifico — sono tre livelli distinti, vanno estesi in cascata |
| `xfs_growfs: specified file is not on an XFS filesystem` | Hai passato il device invece del mount point (unico comando LVM/filesystem che vuole il mount point) |
| Perdita di riferimento al loop device dopo un riavvio | I loop device non sono persistenti di default — dopo un reboot vanno ricreati con `losetup -fP` |

## Perché è rilevante per l'SRE

La gestione dello storage è una delle cause più comuni di incidenti in produzione — "disco pieno" è probabilmente nella top 3 degli alert notturni di qualsiasi SRE. Capire *prima* che uno spazio si esaurisca come estendere un volume senza downtime (o perché in certi casi non è possibile, come il restringimento xfs) è esattamente il tipo di conoscenza che separa chi improvvisa da chi ha un runbook pronto. Ritroverai lo stesso concetto di "pool di storage flessibile" più avanti quando affronterai i **PersistentVolume** di Kubernetes.
