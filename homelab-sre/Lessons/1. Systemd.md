# Lezione 1 — systemd: unit, target, dipendenze

## Teoria (30-45')

### Cos'è una unit

In systemd, praticamente tutto è una "unit": un servizio, un mount, un timer, un socket, un target. Ogni unit è un file di testo (di solito in `/etc/systemd/system/` per quelle custom, `/usr/lib/systemd/system/` per quelle di sistema).

### Le sezioni principali di un file `.service`

```ini
[Unit]
Description=Il mio servizio di prova
After=network.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/mio-script.sh
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

- **`[Unit]`** — metadati e dipendenze.
  - `After=` definisce solo l'*ordine* di avvio (non crea una dipendenza reale).
  - `Wants=` è una dipendenza debole: "se disponibile, avvialo anche".
  - `Requires=` è una dipendenza forte: se quella unit fallisce, fallisce anche la tua.
- **`[Service]`** — come va eseguito il processo.
  - `Type=simple`: il processo principale è quello avviato da `ExecStart`.
  - `Type=oneshot`: esegue e termina, utile per script di setup.
  - `Type=forking`: per demoni vecchio stile che fanno fork.
- **`[Install]`** — cosa succede con `systemctl enable`.
  - `WantedBy=multi-user.target` è l'equivalente moderno del "runlevel 3" di sysvinit.

### I target

Sono unit speciali che raggruppano altre unit — l'equivalente dei runlevel, ma più flessibile.

- `multi-user.target`: sistema avviato, niente GUI.
- `graphical.target`: estende il precedente aggiungendo la parte grafica.

Per vedere le dipendenze di un target:

```bash
systemctl list-dependencies multi-user.target
```

### Perché `After` ≠ `Requires`

Questo è il punto che confonde di più all'inizio. `After=network.target` senza `Requires=` significa "se network.target parte, fallo prima di me" — ma se network.target non parte per qualche motivo, il tuo servizio parte comunque. Se vuoi che il tuo servizio *dipenda* davvero dalla rete, ti servono entrambe le direttive insieme.

## Pratica (75-90')

### 1. Crea lo script base

Crea `/usr/local/bin/mio-monitor.sh`: uno script bash che ogni 5 secondi scrive su stdout un timestamp e l'uso di memoria (`free -h`). Rendilo eseguibile con `chmod +x`. Sarà il "servizio" che gestirai con systemd.

```bash
#!/bin/bash
while true; do
  echo "[$(date '+%Y-%m-%d %H:%M:%S')]"
  free -h
  sleep 5
done
```

### 2. Scrivi la prima unit (Type=simple)

Crea `/etc/systemd/system/mio-monitor.service`:

```ini
[Unit]
Description=Monitor di prova
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/mio-monitor.sh
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Poi ricarica la configurazione:

```bash
sudo systemctl daemon-reload
```

### 3. Avvia, abilita, verifica

```bash
sudo systemctl start mio-monitor
systemctl status mio-monitor      # dovrebbe essere "active (running)"
sudo systemctl enable mio-monitor
systemctl is-enabled mio-monitor
```

### 4. Leggi i log con journalctl

```bash
journalctl -u mio-monitor -f                  # segui i log in tempo reale
journalctl -u mio-monitor --since "10 min ago"
journalctl -u mio-monitor -p err              # solo errori
```

### 5. Crea una seconda unit di tipo oneshot

Crea `/etc/systemd/system/mio-setup.service`, che esegue uno script che scrive un file di lock in `/tmp/mio-setup-done`:

```ini
[Unit]
Description=Setup iniziale

[Service]
Type=oneshot
ExecStart=/usr/local/bin/mio-setup.sh
RemainAfterExit=yes
```

`RemainAfterExit=yes` fa sì che systemd consideri la unit "attiva" anche dopo che il processo è terminato.

### 6. Costruisci una vera dipendenza tra le due unit

Modifica `mio-monitor.service` aggiungendo nella sezione `[Unit]`:

```ini
Requires=mio-setup.service
After=mio-setup.service
```

Poi:

```bash
sudo systemctl daemon-reload
sudo systemctl stop mio-monitor mio-setup
sudo systemctl start mio-monitor
```

Dovresti vedere che systemd avvia automaticamente anche `mio-setup` prima di `mio-monitor`.

### 7. Rompilo di proposito e osserva il journal

Modifica lo script di monitor per uscire con `exit 1` a caso una volta ogni tot cicli. Riavvia il servizio e guarda con `journalctl -u mio-monitor` come systemd lo riavvia da solo grazie a `Restart=on-failure`, quanti tentativi fa e con che intervallo (`RestartSec`).

> Questo meccanismo di restart-con-backoff è concettualmente identico a quello che troverai su Kubernetes quando un pod entra in **CrashLoopBackOff** — vale la pena capirlo bene prima di andare avanti.

### 8. Lista comandi

```bash
systemctl show mio-monitor -p NRestarts       # Numero di riavvii
systemctl list-dependencies multi-user.target # Dipendenze di un target

journalctl -u mio-monitor -f                  # segui i log in tempo reale
journalctl -u mio-monitor --since "10 min ago"
journalctl -u mio-monitor -p err              # solo errori
```
