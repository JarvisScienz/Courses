# Lezione 2 — Utenti, gruppi, permessi, ACL, sudo

## Teoria (30-45')

### Utenti e gruppi: i concetti base

Ogni utente su Linux ha uno **UID** (User ID) e appartiene a un **gruppo primario** più eventuali **gruppi secondari**. Le informazioni vivono in file di testo semplici:

- `/etc/passwd` — utenti (nome, UID, GID primario, home, shell)
- `/etc/group` — gruppi e relativi membri
- `/etc/shadow` — password (hash), leggibile solo da root

```bash
cat /etc/passwd | grep davide
id davide                 # mostra UID, GID, tutti i gruppi
groups davide              # solo i nomi dei gruppi
```

Distinzione importante: **utenti di sistema** (UID < 1000, es. `daemon`, `nginx`) vs **utenti "umani"** (UID ≥ 1000). I servizi che gestirai con systemd spesso girano con un utente di sistema dedicato, non come root — è una best practice di sicurezza che rivedrai spesso.

### I permessi classici (rwx)

Ogni file/directory ha tre terne di permessi: **proprietario**, **gruppo**, **altri**. Ogni terna può avere `r` (read), `w` (write), `x` (execute).

```bash
ls -l /etc/sudoers
# -r--r----- 1 root root ... /etc/sudoers
```

Si leggono così: proprietario `root` può leggere, gruppo `root` può leggere, "altri" non hanno permessi. Su una directory, `x` significa "posso entrarci" (`cd`), non "posso listarla" — è un dettaglio che confonde spesso all'inizio.

**Notazione numerica (ottale):** `r=4, w=2, x=1`, sommati per terna. `755` = `rwxr-xr-x`, `644` = `rw-r--r--`.

```bash
chmod 750 /opt/mio-progetto     # rwxr-x---
chown davide:sviluppatori file.txt
```

### Il limite dei permessi classici

Con rwx puoi assegnare permessi solo a **un** proprietario e **un** gruppo. Cosa fai se vuoi che *due* gruppi diversi abbiano permessi diversi sulla stessa cartella (es. `devops` può scrivere, `readonly-team` può solo leggere)? Qui entrano le **ACL** (Access Control List).

### ACL (Access Control List)

Le ACL estendono il modello classico permettendo regole per utenti/gruppi multipli sullo stesso file.

```bash
getfacl /opt/mio-progetto              # vedi le ACL correnti
setfacl -m u:mario:rwx /opt/mio-progetto        # utente specifico
setfacl -m g:readonly-team:r-x /opt/mio-progetto # gruppo specifico
setfacl -d -m g:devops:rwx /opt/mio-progetto     # ACL di default (ereditata dai nuovi file creati dentro)
```

Nota: se un file ha ACL extra, `ls -l` mostra un `+` dopo i permessi classici (es. `drwxrwx---+`).

### sudo e sudoers

`sudo` permette di eseguire comandi come un altro utente (di solito root) senza condividere la password di root. La configurazione vive in `/etc/sudoers`, ma **non va mai editato direttamente** con un editor qualsiasi: si usa `visudo`, che valida la sintassi prima di salvare (un errore in `/etc/sudoers` può bloccarti fuori dal sistema).

```bash
sudo visudo
```

Sintassi base di una riga in sudoers:

```
utente  host=(utente_target)  comandi
```

Esempi:

```
davide  ALL=(ALL)       ALL              # davide può eseguire qualsiasi comando come qualsiasi utente
mario   ALL=(root)      /usr/bin/systemctl restart mio-monitor   # mario può SOLO riavviare quel servizio
%devops ALL=(root)      NOPASSWD: /usr/bin/docker *               # il gruppo devops, senza password, solo su docker
```

Il `%` davanti indica un gruppo invece di un utente singolo. `NOPASSWD` evita che venga richiesta la password (da usare con cautela, tipicamente per automazioni).

**Best practice**: invece di editare `/etc/sudoers` direttamente, si creano file dedicati in `/etc/sudoers.d/` (uno per progetto/team) — più facili da versionare e da revocare singolarmente.

## Pratica (75-90')

### 1. Crea utenti e gruppi dedicati al progetto

```bash
sudo groupadd homelab-devops
sudo groupadd homelab-readonly

sudo useradd -m -G homelab-devops -s /bin/bash operatore
sudo useradd -m -G homelab-readonly -s /bin/bash osservatore

sudo passwd operatore
sudo passwd osservatore
```

Verifica:

```bash
id operatore
id osservatore
```

### 2. Crea la cartella condivisa del progetto

```bash
sudo mkdir -p /opt/homelab
sudo chown root:homelab-devops /opt/homelab
sudo chmod 770 /opt/homelab
```

A questo punto solo `root` e membri di `homelab-devops` possono accedere. `osservatore` non può ancora entrarci — verificalo:

```bash
sudo -u osservatore ls /opt/homelab   # Permission denied, come atteso
```

### 3. Configura le ACL per dare accesso in sola lettura a un secondo gruppo

```bash
sudo setfacl -m g:homelab-readonly:r-x /opt/homelab
sudo setfacl -d -m g:homelab-readonly:r-x /opt/homelab   # default, per i file futuri
sudo setfacl -d -m g:homelab-devops:rwx /opt/homelab
```

Verifica:

```bash
getfacl /opt/homelab
sudo -u osservatore ls /opt/homelab      # ora funziona
sudo -u osservatore touch /opt/homelab/test.txt   # deve fallire (solo lettura)
sudo -u operatore touch /opt/homelab/test.txt     # deve funzionare
```

### 4. Configura sudo granulare per il gruppo devops

Crea un file dedicato invece di editare `/etc/sudoers` direttamente:

```bash
sudo visudo -f /etc/sudoers.d/homelab-devops
```

Contenuto:

```
%homelab-devops ALL=(root) NOPASSWD: /usr/bin/systemctl restart mio-monitor, /usr/bin/systemctl status mio-monitor
```

Verifica come `operatore`:

```bash
su - operatore
sudo systemctl restart mio-monitor    # deve funzionare senza chiedere password
sudo systemctl restart sshd           # deve essere negato (non è nella lista)
```

### 5. Verifica il comportamento con `sudo -l`

```bash
sudo -l -U operatore     # mostra cosa può fare operatore con sudo
sudo -l -U osservatore   # dovrebbe non avere permessi sudo particolari
```

### 6. Esperimento di rottura controllata

Prova a introdurre un errore di sintassi in un file sudoers *di test* (non in quello principale!) e osserva come `visudo` blocca il salvataggio:

```bash
sudo visudo -f /etc/sudoers.d/test-errore
# scrivi qualcosa di sbagliato tipo: davide ALL=(ALL) ALL ALL ALL
# al salvataggio, visudo segnala l'errore e NON scrive il file
```

Questo è esattamente il motivo per cui non si edita mai `/etc/sudoers` con `nano` o `vim` direttamente.

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| `sudo: command not found` per un comando dentro un percorso custom | Il path nel file sudoers deve essere assoluto ed esatto (systemd/sudo non usano il `$PATH` della shell) |
| Un utente in un nuovo gruppo non ha ancora i permessi | Serve rifare login (i gruppi vengono letti alla creazione della sessione), non basta `groups` |
| ACL che "spariscono" dopo un `cp` | `cp` di default non preserva le ACL: serve `cp -p` o `cp --preserve=all` |
| Bloccato fuori da sudo dopo una modifica manuale a `/etc/sudoers` | Da qui la regola ferrea: sempre e solo `visudo` |

## Perché è rilevante per l'SRE

Quando più persone (o più pipeline automatizzate) accedono agli stessi server, la differenza tra "chi può fare cosa" non è un dettaglio burocratico: è la prima linea di difesa contro incidenti causati da permessi troppo larghi. Le stesse logiche che hai appena praticato a mano (utente dedicato, permessi minimi, sudo granulare) le ritroverai identiche più avanti sotto altre vesti: **RBAC in Kubernetes** e **IAM roles** nel cloud sono concettualmente lo stesso principio del "least privilege" applicato a un livello diverso.
