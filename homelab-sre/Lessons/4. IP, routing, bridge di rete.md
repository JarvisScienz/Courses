# Lezione 4 — TCP/IP, routing, bridge di rete

## Teoria (45')

### Il modello TCP/IP in breve (quanto basta per essere operativi)

Non serve la teoria da manuale universitario, ma alcuni concetti tornano continuamente da qui in poi (Docker, Kubernetes, troubleshooting):

- **Livello di rete (IP)**: indirizzi, routing tra reti diverse.
- **Livello di trasporto (TCP/UDP)**: porte, connessioni, affidabilità (TCP) vs velocità senza garanzie (UDP).
- **Livello di collegamento (Ethernet, ARP)**: indirizzi MAC, comunicazione sulla stessa rete fisica/virtuale.

Il motivo per cui te lo ripeto qui: un **bridge** lavora al livello di collegamento (livello 2), *non* al livello IP. Questo è il concetto chiave di tutta la lezione.

### Indirizzamento IP e subnetting, l'essenziale

Un indirizzo IPv4 + una subnet mask definiscono quali indirizzi sono "nella stessa rete" (raggiungibili direttamente) e quali richiedono un router.

```
192.168.100.0/24
```

- `/24` = 255.255.255.0 → 256 indirizzi (192.168.100.0–255), di cui 254 utilizzabili (il primo è l'indirizzo di rete, l'ultimo il broadcast).
- Due host sono sulla stessa rete se, applicando la maschera, ottengono lo stesso "network address".

```bash
ip addr show                     # indirizzi IP configurati
ip route show                    # tabella di routing
```

Una tabella di routing tipica:

```
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50
```

Si legge: "per raggiungere 192.168.1.0/24 esco direttamente da eth0; per tutto il resto (default) passo dal router 192.168.1.1".

### Cos'è un bridge e perché ti serve per le VM

Un **bridge Linux** è uno switch software: collega più interfacce di rete (fisiche o virtuali) facendole comportare come se fossero sulla stessa rete fisica, a livello 2 (MAC address), non livello 3 (IP).

Perché serve per KVM/libvirt: quando crei una VM con un'interfaccia di rete, quella interfaccia virtuale deve "agganciarsi" a qualcosa per parlare con il resto della rete. Le opzioni tipiche sono:

1. **NAT** (quello che libvirt crea di default, `virbr0`): le VM stanno dietro un NAT, come dispositivi domestici dietro un router. Possono uscire verso l'esterno, ma dall'esterno non sono raggiungibili direttamente. Semplice, ma limitante per un homelab dove vuoi che le VM si comportino come server "veri" sulla tua rete.
2. **Bridge**: colleghi l'interfaccia fisica del PC (es. `enp3s0`) e le interfacce virtuali delle VM allo stesso bridge software. Le VM ottengono un IP nella *tua* rete di casa/lab, come se fossero macchine fisiche collegate allo switch. Questo è ciò che ti serve per il resto del percorso (bastion host, nodi K8s raggiungibili tra loro e da te).

```
[eth fisica] ─┐
              ├── bridge (br0) ── [vNIC VM1] ── [vNIC VM2] ── ...
[vNIC host]  ─┘
```

Il bridge stesso ha un IP (quello che prima aveva l'interfaccia fisica), e tutto quello che ci è collegato sopra condivide la stessa rete L2.

### NetworkManager vs configurazione manuale

Fedora usa NetworkManager di default. Puoi configurare tutto con `nmcli` (persistente, sopravvive al riavvio) oppure con `ip` (immediato ma non persistente, utile per test rapidi). In questa lezione vedrai entrambi, ma per la configurazione definitiva userai `nmcli`.

## Pratica (75-90')

> **Attenzione prima di iniziare**: se lavori da remoto (SSH) sul PC Fedora, cambiare la configurazione di rete può interromperti la connessione. Fai questi esercizi da tastiera/monitor collegati direttamente, oppure assicurati di avere un modo per riconnetterti (es. accesso fisico, IPMI, o una seconda interfaccia di rete dedicata alla gestione).

### 1. Osserva la configurazione di rete attuale

```bash
ip addr show
ip route show
nmcli device status
nmcli connection show
```

Annota il nome della tua interfaccia fisica (es. `enp3s0`, `eth0`) e il nome della connessione attiva mostrata da `nmcli connection show` — ti serviranno tra poco.

### 2. Crea un bridge temporaneo con `ip` (non persistente, solo per capire il meccanismo)

```bash
sudo ip link add name br-test type bridge
sudo ip link set br-test up
sudo ip link set enp3s0 master br-test    # aggancia l'interfaccia fisica al bridge
ip link show br-test
```

A questo punto, se la tua interfaccia fisica aveva un IP statico assegnato direttamente, l'hai perso (ora appartiene al bridge). Questo è volutamente un esperimento "usa e getta": rimuovilo subito dopo aver osservato il comportamento:

```bash
sudo ip link set enp3s0 nomaster
sudo ip link delete br-test
```

### 3. Crea il bridge definitivo con `nmcli` (persistente)

```bash
# Crea il bridge
sudo nmcli connection add type bridge ifname br0 con-name br0

# Configuralo con IP statico (adatta alla tua rete)
sudo nmcli connection modify br0 ipv4.addresses 192.168.1.50/24
sudo nmcli connection modify br0 ipv4.gateway 192.168.1.1
sudo nmcli connection modify br0 ipv4.dns "192.168.1.1"
sudo nmcli connection modify br0 ipv4.method manual

# Aggancia l'interfaccia fisica come slave del bridge
sudo nmcli connection add type ethernet ifname enp3s0 master br0 con-name br0-slave

# Attiva
sudo nmcli connection up br0
```

### 4. Verifica che tutto funzioni

```bash
ip addr show br0                 # dovrebbe avere l'IP che hai assegnato
ip route show                    # il default gateway ora passa da br0
ping -c 3 192.168.1.1            # gateway raggiungibile
ping -c 3 8.8.8.8                # uscita verso internet
```

Se qualcosa non va e hai perso la connettività, da console locale puoi tornare indietro:

```bash
sudo nmcli connection down br0
sudo nmcli connection delete br0 br0-slave
sudo nmcli connection up "Wired connection 1"    # o il nome originale annotato al punto 1
```

### 5. Verifica cosa succede a livello 2

```bash
bridge link show                 # interfacce collegate al bridge
bridge fdb show br br0           # tabella MAC address appresi dal bridge
```

Genera un po' di traffico (es. un ping da un altro dispositivo verso il tuo PC) e rilancia `bridge fdb show`: vedrai comparire nuovi MAC address appresi dinamicamente — è lo stesso meccanismo di apprendimento di uno switch fisico.

### 6. Prepara il terreno per libvirt (anticipazione della Fase 2)

Verifica che libvirt possa vedere il bridge (non serve ancora usarlo, solo confermare che è visibile):

```bash
ip link show type bridge
```

Quando nella prossima fase creerai le VM con `virt-install`, potrai specificare `--network bridge=br0` invece del NAT di default: le VM otterranno un IP direttamente sulla tua rete, esattamente come una macchina fisica.

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| Perdita di connettività subito dopo `master enp3s0 br-test` | Normale: l'IP era assegnato all'interfaccia fisica, ora appartiene al bridge. Serve riassegnarlo al bridge, non all'interfaccia |
| `nmcli` dice "connection successfully activated" ma non c'è internet | Manca `ipv4.gateway` o `ipv4.dns`, oppure la modalità è rimasta su `auto` invece di `manual` con IP statico configurato |
| Due default gateway in `ip route show` dopo aver creato il bridge | La vecchia connessione dell'interfaccia fisica è ancora attiva in parallelo — va disattivata (`nmcli connection down`) |
| Il bridge non impara i MAC address (`bridge fdb show` vuoto) | Nessun traffico è ancora passato, oppure l'interfaccia slave non è effettivamente `up` — controlla con `ip link show` |

## Perché è rilevante per l'SRE

Il bridge di rete è la base silenziosa su cui poggerà tutto il resto del percorso: le VM della Fase 2, i nodi Kubernetes della Fase 4, i servizi che esporrai con Ingress — tutto passa da qui in termini di raggiungibilità di rete. Capire la differenza tra NAT e bridge, e sapere leggere una tabella di routing sotto pressione (quando un servizio "non risponde" e devi capire se è un problema applicativo o di rete), è una delle competenze che distingue più nettamente un SRE da chi si ferma al livello applicativo.
