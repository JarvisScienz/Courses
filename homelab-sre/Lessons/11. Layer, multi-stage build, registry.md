# Lezione 11 — Layer, multi-stage build, registry: immagini piccole, veloci da costruire e distribuite da un registry tuo

> **Dove siamo**: nella lezione 10 hai installato Docker su `app`, visto che un container è un processo con namespace e cgroups e scritto un primo `Dockerfile` per `app-demo` (v0.1 root, v0.2 `USER node`). Funziona, ma l'immagine è grossa, il build rifà tutto a ogni modifica e l'immagine esiste **solo su `app`**. Oggi risolvi i tre problemi: capisci i **layer** e la cache, scrivi un **Dockerfile multi-stage** che butta via ciò che serve solo per costruire, e metti su un **registry privato** sulla VM `storage` da cui qualunque macchina del lab può fare `pull`. Il registry è il primo mattone della catena build → registry → deploy che userai con Kubernetes (Fase 4) e nelle pipeline CI/CD (Fase 6).

## Teoria (30-45')

### Cos'è un layer, davvero

Un'immagine è una pila di **layer**: ogni layer è un archivio tar dei file che un'istruzione del `Dockerfile` ha aggiunto, modificato o cancellato rispetto al layer sotto. Ogni layer ha un **digest** `sha256:...` calcolato sul contenuto: due immagini che condividono un layer lo memorizzano **una volta sola** su disco e lo scaricano una volta sola.

| Istruzione | Crea un layer di file? | Note |
|---|---|---|
| `FROM` | Importa i layer dell'immagine base | È la parte più pesante |
| `RUN`, `COPY`, `ADD` | **Sì** | Il layer contiene ciò che il comando ha scritto |
| `ENV`, `WORKDIR`, `USER`, `EXPOSE`, `CMD`, `ENTRYPOINT`, `LABEL` | No (solo metadati) | Non pesano, ma contano nella cache |

Due conseguenze pratiche che ti serviranno oggi:

1. **I layer sono immutabili e additivi.** Se un `RUN` scarica 200 MB e un `RUN` successivo li cancella, l'immagine pesa comunque 200 MB: il file è ancora nel layer sotto, il layer sopra aggiunge solo un "segno di cancellazione" (whiteout). Cancellare in un layer **dopo** non libera spazio. Va fatto **nello stesso `RUN`** (`apt-get install ... && rm -rf /var/lib/apt/lists/*`) oppure evitato con un multi-stage.
2. **Un file segreto copiato in un layer resta nell'immagine per sempre**, anche se lo cancelli dopo. `docker history` e `docker save` lo mostrano. Mai `COPY .env`, mai un token in un `ARG`/`ENV`: per i segreti di build esistono i `--mount=type=secret` di BuildKit.

### La cache di build

Docker (BuildKit) riusa un layer se **l'istruzione e tutti i suoi input** sono identici al build precedente. Per `COPY` l'input è il contenuto dei file copiati. Appena un'istruzione cambia, **tutte quelle successive** vengono rieseguite.

```
COPY . .              ← cambi una riga di codice
RUN npm install       ← cache invalidata: reinstalla tutto, ogni volta
```

contro

```
COPY package*.json ./ ← cambia solo quando cambiano le dipendenze
RUN npm ci            ← cache riusata nel 95% dei build
COPY . .              ← cambia a ogni modifica, ma è economico
```

Regola: **metti in alto ciò che cambia raramente (sistema, dipendenze), in basso ciò che cambia spesso (il tuo codice)**. In CI questo vale minuti ogni giorno; per un SRE vale anche meno traffico verso internet e meno carico sul registry.

`.dockerignore` fa parte della stessa storia: tutto ciò che mandi al demone come *build context* (`.git`, `node_modules`, log) rallenta il build e invalida la cache di `COPY . .` quando cambia.

### Perché le immagini sono grosse (e perché importa)

Un'immagine grande significa: pull lento (un nodo Kubernetes nuovo impiega minuti prima di avviare il Pod), più disco in `/var/lib/docker`, più **superficie d'attacco** (ogni pacchetto in più è una CVE potenziale: compilatori, `curl`, shell, git che a runtime non servono) e scale-out più lento sotto carico.

Tre leve, dalla più semplice:

| Leva | Esempio | Effetto |
|---|---|---|
| Base più piccola | `node:22` (Debian, ~1 GB) → `node:22-alpine` (~150 MB) → *distroless* (~100 MB, senza shell) | Riduce il pavimento |
| Installare solo ciò che serve a runtime | `npm ci --omit=dev` | Niente strumenti di test e build |
| **Multi-stage build** | Costruisci in uno stage "pesante", copia **solo il risultato** in uno stage finale "leggero" | Compilatori, `devDependencies`, sorgenti non entrano nell'immagine finale |

*Nota su Alpine*: usa `musl` invece di `glibc`. Va benissimo per Node puro; per moduli nativi precompilati per glibc (alcuni driver, `sharp`, Python con wheel) può dare problemi strani: in quel caso `-slim` (Debian ridotto) è il compromesso.

### Multi-stage build

Un solo `Dockerfile` con **più `FROM`**. Ogni `FROM` apre uno *stage*; solo l'**ultimo** diventa l'immagine finale, gli altri servono per costruire e vengono scartati. Da uno stage precedente si copiano file con `COPY --from=<stage>`.

```dockerfile
FROM node:22-alpine AS build        # stage 1: ha tutto ciò che serve per costruire
...
FROM node:22-alpine AS runtime      # stage 2: immagine finale
COPY --from=build /app/dist ./dist  # prende solo il risultato
```

Vantaggi ulteriori:
- Con `docker build --target build .` costruisci **solo fino a uno stage** (utile per eseguire i test in CI senza produrre l'immagine finale).
- Gli stage indipendenti sono costruiti **in parallelo** da BuildKit.
- Lo stesso schema vale per React: stage `build` (Node, `npm run build`) → stage finale `nginx:alpine` che serve solo i file statici. Da 1 GB di toolchain a ~40 MB.

### Tag, digest e immutabilità

- Un **tag** (`app-demo:0.3`) è un puntatore **mobile**: puoi rifare `push` dello stesso tag con un'immagine diversa. 
- Un **digest** (`app-demo@sha256:9f2c...`) identifica il contenuto e **non cambia mai**. In produzione ciò che vuoi eseguire è il digest (o un tag che non muovi mai).
- Strategia sensata: tag di versione immutabile (`0.3.1`) + eventualmente il commit Git (`0.3.1-a1b2c3d`). Evita `latest`: non dice cosa sta girando e non permette il rollback.
- Un'immagine multi-architettura ha un **manifest list** (un digest che punta a un digest per `amd64`, uno per `arm64`...): l'`exec format error` della lezione 10 nasce qui.

### Il registry

Un **registry** è un server HTTP che implementa l'API *OCI Distribution* (`/v2/...`) e conserva due cose: i **blob** (i layer, indirizzati per digest) e i **manifest** (l'elenco di layer + configurazione, indirizzato per tag e digest).

Un nome d'immagine completo ha questa forma:

```
registry.lab:5000 / app-demo : 0.3
└── registry ────┘ └─ repo ─┘ └ tag
```

Se non indichi il registry, Docker presume **Docker Hub** (`docker.io/library/...`). `docker push` carica solo i layer che il registry **non ha già** (confronto per digest): il secondo push della stessa immagine con una modifica minima trasferisce pochi KB.

**Perché uno privato?** Rate limit di Docker Hub per i pull anonimi, immagini interne che non vuoi pubblicare, velocità sulla LAN, controllo su chi scarica cosa, funzionamento a internet staccata. Nel cloud lo stesso ruolo lo fanno ECR, GCR/Artifact Registry, ACR, GHCR.

**TLS e "insecure registry".** Docker accetta di parlare in chiaro (HTTP) solo con `localhost` e con registry elencati in `insecure-registries`. Per tutto il resto richiede HTTPS con un certificato che la macchina client riconosce. Per il lab hai due strade:
- **`insecure-registries`** in `daemon.json`: veloce, ma anche tutto il traffico (e le credenziali) in chiaro. Va bene solo su una rete di prova.
- **Certificato autofirmato + CA di fiducia** in `/etc/docker/certs.d/<host:porta>/ca.crt`: poco più lungo, ed è ciò che fai davvero in produzione (con una CA interna). Lo fai oggi.

> Il registry di base (`registry:2`) **non ha autenticazione** né interfaccia web. Chiunque raggiunga la porta può fare `push` e `pull`. Nel lab è accettabile perché sta su una VM con firewall; sappi che in produzione si mette `htpasswd`/token auth o si usa un prodotto (Harbor, Nexus, il registry del cloud).

### 1. Misura il punto di partenza

Prima di ottimizzare, **misura**. Sulla VM `app`:

```bash
docker pull node:22
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.Size}}' | grep -E 'node|app-demo'

docker history --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' app-demo:0.2 | head
```

Annota la dimensione di `node:22`, di `node:22-alpine` e di `app-demo:0.2`. `docker history` elenca i layer dall'alto verso il basso con la loro dimensione: trova quale pesa di più (quasi sempre quello della base). Poi:

```bash
docker run --rm app-demo:0.2 sh -c 'du -sh /app /app/node_modules 2>/dev/null; ls /usr/local/lib/node_modules'
```

Quanto dei MB dell'immagine è la tua app? Il resto è l'ambiente (Node, npm, Alpine).

### 2. Tocca con mano la cache

Fai un build "a freddo" e uno "a caldo", poi cambia una riga di codice:

```bash
cd ~/homelab/app-demo
time docker build -t app-demo:cache-test .          # tutto in cache: pochi secondi
echo "// $(date +%s)" >> server.js                  # modifica minima al codice
time docker build -t app-demo:cache-test .          # ricostruisce solo da "COPY server.js" in poi
```

Nell'output di BuildKit cerca le righe `CACHED [3/5] ...` contro quelle eseguite. Con il `Dockerfile` della lezione 10 (`COPY package.json` → `npm install` → `COPY server.js`) `npm install` resta in cache: è l'ordine giusto.

Ora rompilo di proposito per vedere la differenza. In un file separato:

```bash
cat > Dockerfile.bad <<'EOF'
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm install --omit=dev
USER node
CMD ["node", "server.js"]
EOF

time docker build -f Dockerfile.bad -t app-demo:bad .
echo "// $(date +%s)" >> server.js
time docker build -f Dockerfile.bad -t app-demo:bad .   # npm install rifatto da zero
```

Annota i due tempi. Su un progetto reale con 500 dipendenze la differenza è di minuti per ogni commit. Poi `rm Dockerfile.bad`.

### 3. Aggiungi uno step di build all'app

Per rendere reale il multi-stage, l'app deve avere qualcosa da *costruire* e delle dipendenze di sviluppo. Aggiungi `esbuild` come `devDependency` e uno script che produce un unico file `dist/server.js`:

```bash
cd ~/homelab/app-demo
mkdir -p src && mv server.js src/server.js
sed -i '/^\/\/ [0-9]*$/d' src/server.js                 # toglie le righe di prova della cache

cat > package.json <<'EOF'
{
  "name": "app-demo",
  "version": "0.3.0",
  "private": true,
  "main": "dist/server.js",
  "scripts": {
    "build": "esbuild src/server.js --bundle --platform=node --target=node22 --minify --outfile=dist/server.js",
    "start": "node dist/server.js"
  },
  "devDependencies": {
    "esbuild": "0.25.0"
  }
}
EOF

npm install                    # genera package-lock.json (versioni esatte)
npm run build && ls -lh dist/
```

`package-lock.json` va nel repository: `npm ci` (che userai nel `Dockerfile`) installa **esattamente** le versioni del lock e fallisce se non coincidono con `package.json`. È la riproducibilità del build.

Prova a mano che l'app costruita funzioni: `node dist/server.js &` poi `curl -s localhost:3000` e `kill %1`.

### 4. Il Dockerfile multi-stage

```bash
cat > Dockerfile <<'EOF'
# syntax=docker/dockerfile:1

# ---- Stage 1: dipendenze (cache stabile) ----
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

# ---- Stage 2: build ----
FROM deps AS build
COPY src ./src
RUN npm run build

# ---- Stage 3: immagine finale ----
FROM node:22-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 3000
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "dist/server.js"]
EOF

cat > .dockerignore <<'EOF'
node_modules
dist
npm-debug.log
.git
.env
Dockerfile*
EOF
```

Cosa guardare nel file:
- **Tre stage**: `deps` cambia solo se cambia il lock; `build` solo se cambia `src/`; `runtime` è quello che esce.
- `--mount=type=cache` tiene la cache di npm **fuori dall'immagine** e la riusa tra build (BuildKit).
- Lo stage finale **non ha** `node_modules`, `esbuild`, `package.json` né i sorgenti: solo `dist/server.js` (l'app non ha dipendenze a runtime perché esbuild le ha incorporate nel bundle). Ha `USER node` come in lezione 10.
- `HEALTHCHECK` fa sì che `docker ps` mostri `healthy`/`unhealthy`. In Kubernetes lo sostituiscono le *probe* (liveness/readiness, lezione 17), ma il principio è lo stesso: **non basta che il processo esista, deve rispondere**. `wget` c'è in Alpine/busybox; in un'immagine distroless non lo avresti e useresti una probe esterna.

Costruisci e confronta:

```bash
time docker build -t app-demo:0.3 .
docker images app-demo
docker history app-demo:0.3
```

Confronta la dimensione con `0.2`. Dovresti vedere meno MB, perché sono spariti `npm`'s cache, `node_modules` e i sorgenti. Poi la prova che il multi-stage non ha lasciato nulla dietro:

```bash
docker run --rm app-demo:0.3 ls -la /app
docker run --rm app-demo:0.3 ls /app/node_modules 2>&1 | head -2     # No such file or directory
```

Costruisci anche **solo il primo stage** per vedere cosa verrebbe buttato:

```bash
docker build --target build -t app-demo:build-stage .
docker images app-demo
docker run --rm app-demo:build-stage ls /app
```

Lo stage `build` pesa molto di più. È proprio quello che *non* vuoi mandare in produzione. Dopo il confronto: `docker rmi app-demo:build-stage app-demo:bad app-demo:cache-test`.

### 5. Avvio e healthcheck

```bash
docker rm -f demo 2>/dev/null
docker run -d --name demo -p 8080:3000 app-demo:0.3
sleep 8; docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'      # (healthy)
curl -s localhost:8080

```

Verifica che i segnali funzionino ancora (lezione 10) con la forma exec:

```bash
time docker stop demo           # veloce: PID 1 è node, non una shell
```

Quindi rompi di proposito l'healthcheck per vederlo cambiare stato: `docker run -d --name sick -e PORT=4000 app-demo:0.3` (l'app ascolta su 4000, il check interroga la 3000) e dopo ~40 s `docker ps` mostra `unhealthy`. Nota che **Docker non lo riavvia** da solo: lo segnala. Chi agisce è l'orchestratore. `docker rm -f sick demo`.

### 6. Verifica cosa c'è dentro: layer e segreti

```bash
docker history --no-trunc app-demo:0.3 | head -15
docker save app-demo:0.3 -o /tmp/app-demo.tar
mkdir /tmp/img && tar -xf /tmp/app-demo.tar -C /tmp/img
ls /tmp/img /tmp/img/blobs/sha256 | head
cat /tmp/img/manifest.json | python3 -m json.tool | head -30
rm -rf /tmp/img /tmp/app-demo.tar
```

`docker save` produce un tar OCI: dentro vedi `manifest.json`, la *config* e un blob per layer. È la dimostrazione che un'immagine è solo un insieme di tar con un indice. Ora il caso "segreto nel layer":

```bash
mkdir /tmp/leak && cd /tmp/leak
echo "PASSWORD=hunter2" > secret.txt
cat > Dockerfile <<'EOF'
FROM alpine:3.20
COPY secret.txt /secret.txt
RUN rm /secret.txt
CMD ["sleep","3600"]
EOF
docker build -t leak:test .
docker run --rm leak:test ls /secret.txt              # non c'è: sembra cancellato
docker save leak:test -o leak.tar && mkdir x && tar -xf leak.tar -C x
for b in x/blobs/sha256/*; do tar -tf "$b" 2>/dev/null | grep -q '^secret.txt$' && echo "TROVATO in $b"; done
cd ~ && rm -rf /tmp/leak && docker rmi leak:test
```

Il file non c'è nel container, ma **è dentro il layer del `COPY`**. Chiunque scarichi l'immagine lo estrae. Per questo i segreti non entrano mai nel build.

### 7. Il registry privato su `storage`

Dall'host (o da `app`, con `ssh storage.lab`). Su `storage` installa Docker come in lezione 10 (stessi 5 comandi del repo ufficiale; puoi anche clonare la VM `app` post-lezione-10 partendo dalla golden image, ma qui basta installare). Poi:

```bash
ssh storage.lab
sudo mkdir -p /srv/registry/{data,certs}
```

**Certificato autofirmato con SAN** (il nome o l'IP con cui i client si collegano **devono** comparire nei SAN, altrimenti Go rifiuta il certificato anche se è "di fiducia"):

```bash
sudo openssl req -x509 -newkey rsa:4096 -sha256 -days 365 -nodes \
  -keyout /srv/registry/certs/registry.key \
  -out    /srv/registry/certs/registry.crt \
  -subj "/CN=registry.lab" \
  -addext "subjectAltName=DNS:registry.lab,IP:192.168.1.53"
sudo openssl x509 -in /srv/registry/certs/registry.crt -noout -subject -dates -ext subjectAltName
```

Avvia il registry con i certificati, i dati su disco e il delete abilitato (serve per la pulizia, punto 10):

```bash
docker run -d --name registry --restart unless-stopped \
  -p 5000:5000 \
  -v /srv/registry/data:/var/lib/registry:Z \
  -v /srv/registry/certs:/certs:ro,Z \
  -e REGISTRY_HTTP_TLS_CERTIFICATE=/certs/registry.crt \
  -e REGISTRY_HTTP_TLS_KEY=/certs/registry.key \
  -e REGISTRY_STORAGE_DELETE_ENABLED=true \
  registry:2

docker ps --filter name=registry
docker logs registry | tail -5
```

Note:
- `-v host:container` è un **bind mount**: i layer sono su `/srv/registry/data` della VM, quindi sopravvivono a `docker rm`. I volumi veri (e le differenze) sono la lezione 12.
- `:Z` dice a Docker di etichettare la cartella per SELinux (lezione 7: senza, `Permission denied` anche con permessi giusti).
- `--restart unless-stopped`: il registry risale dopo un reboot.

Apri la porta nel firewall del guest (lezione 5) **solo dalla LAN** che ti serve:

```bash
sudo firewall-cmd --permanent --add-port=5000/tcp
sudo firewall-cmd --reload
sudo systemctl restart docker           # il reload può aver tolto le regole di Docker (lezione 10)
docker start registry 2>/dev/null
```

> Se `firewall-cmd --reload` fa sparire la raggiungibilità del container, è la stessa trappola dell'elenco errori della lezione 10: Docker va riavviato. In un'installazione "vera" lo metteresti in un'unit systemd o in uno script di deploy.

**Il nome**. Dal punto di vista del client il registry si chiama `registry.lab`. Aggiungi il record alla zona `.lab` servita da dnsmasq sull'host (lezione 6), poi ricarica e verifica:

```bash
# sull'host, nel file di configurazione dnsmasq del lab
#   address=/registry.lab/192.168.1.53       (oppure host-record=registry.lab,192.168.1.53)
sudo dnsmasq --test && sudo systemctl restart dnsmasq
dig +short registry.lab @192.168.1.50
```

**Prova la porta e il TLS dall'host**:

```bash
nc -zv registry.lab 5000
curl -sv https://registry.lab:5000/v2/ 2>&1 | grep -E "SSL certificate|certificate verify|HTTP/"
```

Fallisce con `certificate verify failed`: è atteso, l'host non conosce ancora la CA. Con `curl --cacert registry.crt` funzionerebbe. Ottieni il certificato dall'host e dai fiducia **solo a Docker** (non a tutto il sistema):

```bash
scp storage.lab:/srv/registry/certs/registry.crt ~/registry.crt      # (se serve: sudo cat | ssh ... tee)
curl -s --cacert ~/registry.crt https://registry.lab:5000/v2/ && echo OK    # {} OK
```

### 8. Fai fiducia al certificato su `app`

Su `app` Docker cerca la CA per ogni registry in `/etc/docker/certs.d/<host>:<porta>/`:

```bash
ssh app.lab
sudo mkdir -p /etc/docker/certs.d/registry.lab:5000
scp storage.lab:/srv/registry/certs/registry.crt /tmp/registry.crt
sudo cp /tmp/registry.crt /etc/docker/certs.d/registry.lab:5000/ca.crt
```

Non serve riavviare Docker per le `certs.d`. Ora il giro completo:

```bash
docker tag app-demo:0.3 registry.lab:5000/app-demo:0.3
docker push registry.lab:5000/app-demo:0.3
```

Nell'output di `push` vedi un `Pushed` per ogni layer e alla fine il **digest**:

```
0.3: digest: sha256:b1f8...e29a size: 1572
```

Rifai il push con un secondo tag (stessi layer): `docker tag app-demo:0.3 registry.lab:5000/app-demo:stable && docker push registry.lab:5000/app-demo:stable`. Stavolta ogni layer dice `Layer already exists` e viene caricato solo il manifest: è la deduplicazione per digest.

### 9. Interroga il registry: è solo HTTP

```bash
curl -s --cacert ~/registry.crt https://registry.lab:5000/v2/_catalog
curl -s --cacert ~/registry.crt https://registry.lab:5000/v2/app-demo/tags/list
curl -sI --cacert ~/registry.crt \
  -H 'Accept: application/vnd.oci.image.manifest.v1+json, application/vnd.docker.distribution.manifest.v2+json' \
  https://registry.lab:5000/v2/app-demo/manifests/0.3 | grep -i -E 'HTTP|digest'
```

Il header `Docker-Content-Digest` è il digest dell'immagine. Sul disco di `storage`:

```bash
ssh storage.lab 'sudo find /srv/registry/data -maxdepth 6 -type d | head -20; sudo du -sh /srv/registry/data'
```

Rivedi la struttura `repositories/app-demo/_manifests/tags/...` e `blobs/sha256/..`: il registry è una cartella di file. **Quella cartella è tutto da salvare** se vuoi un backup del registry (lezione 24: una snapshot della VM ≠ backup).

### 10. Pull da un'altra macchina e per digest

Dall'host (o da `bastion`, dopo aver installato Docker e copiato la CA come al punto 8) simula un nodo che non ha mai visto l'immagine:

```bash
docker pull registry.lab:5000/app-demo:0.3
docker run -d --name from-registry -p 9090:3000 registry.lab:5000/app-demo:0.3
curl -s localhost:9090
docker rm -f from-registry
```

Poi il pull per **digest**, l'unico riferimento che non può cambiare sotto i piedi:

```bash
DIGEST=$(docker inspect --format '{{index .RepoDigests 0}}' registry.lab:5000/app-demo:0.3)
echo $DIGEST
docker rmi registry.lab:5000/app-demo:0.3 registry.lab:5000/app-demo:stable
docker pull $DIGEST
```

Prova il caso pericoloso del tag mobile: costruisci una versione diversa, **ri-etichettala con lo stesso tag** e osserva che il digest cambia.

```bash
docker tag app-demo:0.2 registry.lab:5000/app-demo:0.3
docker push registry.lab:5000/app-demo:0.3
curl -sI --cacert ~/registry.crt -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  https://registry.lab:5000/v2/app-demo/manifests/0.3 | grep -i digest     # digest DIVERSO
docker pull $DIGEST                                                         # il vecchio esiste ancora
```

Il tag `0.3` ora punta a un'altra cosa; chi aveva `$DIGEST` ha ancora l'immagine giusta. Rimetti le cose a posto: `docker tag app-demo:0.3 registry.lab:5000/app-demo:0.3 && docker push registry.lab:5000/app-demo:0.3`. Questa è la ragione per cui in produzione si pubblicano tag **immutabili** e le pipeline fanno riferimento al digest.

### 11. Pulizia del registry (garbage collection)

Un registry cresce solo. Cancellare un tag non libera disco: i blob restano finché non si lancia il *garbage collector*.

```bash
DIG=$(curl -sI --cacert ~/registry.crt -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  https://registry.lab:5000/v2/app-demo/manifests/stable | awk -F': ' 'tolower($1)=="docker-content-digest"{print $2}' | tr -d '\r')
curl -s -X DELETE --cacert ~/registry.crt https://registry.lab:5000/v2/app-demo/manifests/$DIG -o /dev/null -w '%{http_code}\n'   # 202
ssh storage.lab 'sudo du -sh /srv/registry/data; docker exec registry registry garbage-collect --dry-run /etc/docker/registry/config.yml | tail -5'
ssh storage.lab 'docker exec registry registry garbage-collect /etc/docker/registry/config.yml | tail -3; sudo du -sh /srv/registry/data'
```

Annota la dimensione prima e dopo. In produzione la GC si esegue con il registry in sola lettura (o con un finestra di manutenzione) e con una politica di retention (es. tieni le ultime N versioni e quelle in uso). Un registry pieno è un altro "no space left on device": aggiungilo a `NOTES.md` accanto al caso di `/var/lib/docker`.

### 12. Se non vuoi il TLS (e perché non dovresti)

Per sapere cosa sta succedendo, prova il percorso "insecure" una volta, su `app`:

```bash
sudo mv /etc/docker/certs.d/registry.lab:5000 /root/certs.d.bak
docker pull registry.lab:5000/app-demo:0.3               # x509: certificate signed by unknown authority
```

`x509: certificate signed by unknown authority` è l'errore che incontrerai ogni volta che una CA interna non è distribuita al client (anche su nodi Kubernetes). La scorciatoia sarebbe `{"insecure-registries":["registry.lab:5000"]}` in `/etc/docker/daemon.json` + `systemctl restart docker`: **non farlo**; ripristina la cartella (`sudo mv /root/certs.d.bak /etc/docker/certs.d/registry.lab:5000`) e verifica che il pull torni a funzionare.

## Errori comuni da conoscere

| Sintomo | Causa probabile |
|---|---|
| `x509: certificate signed by unknown authority` | Il client non ha la CA in `/etc/docker/certs.d/<host:porta>/ca.crt` (o la cartella ha il nome sbagliato: deve includere la **porta**) |
| `x509: certificate is valid for X, not registry.lab` | Il certificato non ha il nome/IP usato nei **SAN**: rigenera con `-addext subjectAltName=...` |
| `http: server gave HTTP response to HTTPS client` | Il registry parla HTTP ma il client si aspetta HTTPS (TLS non configurato sul server, oppure porta sbagliata) |
| `connection refused` / timeout su `registry.lab:5000` | Container fermo, porta non aperta nel firewall del guest (`firewall-cmd --list-ports`), DNS che punta alla macchina sbagliata (`dig registry.lab`) |
| `denied: requested access to the resource is denied` | Il nome non include il registry: `docker push app-demo:0.3` va su Docker Hub. Serve `registry.lab:5000/app-demo:0.3` |
| `manifest unknown` | Il tag o il digest non esiste nel registry (controlla `/v2/<repo>/tags/list`) |
| Il build è lento a ogni modifica | `COPY . .` prima delle dipendenze, oppure manca il `.dockerignore` (build context enorme) |
| L'immagine finale pesa quanto quella di build | Hai copiato `node_modules` o i sorgenti dallo stage di build; oppure lo stage finale parte da `FROM build` invece che da un `FROM` pulito |
| `COPY --from=build ...: not found` | Il percorso nello stage di build è sbagliato (`WORKDIR` diverso) o `npm run build` non ha prodotto l'output dove pensavi |
| `npm ci` fallisce con "package.json and package-lock.json are not in sync" | Hai modificato `package.json` senza rigenerare il lock: `npm install` in locale e commit del lock |
| Il `rm` in un `RUN` successivo non riduce l'immagine | I layer sono additivi: cancella nello **stesso** `RUN` o usa un multi-stage |
| Un segreto è finito nell'immagine | È stato copiato o passato come `ARG`/`ENV` in un layer: ruota il segreto, ricostruisci, usa `--mount=type=secret` |
| Il container resta `unhealthy` ma nessuno lo riavvia | Docker standalone segnala soltanto; è l'orchestratore (Kubernetes, o un processo che legge lo stato) a reagire |
| `Permission denied` scrivendo nel volume del registry | SELinux: manca `:Z` (o `chcon`/`semanage fcontext` per la cartella), oppure permessi Unix sulla cartella |
| Dopo `firewall-cmd --reload` il registry non è più raggiungibile | Le regole di Docker sono state rimosse dal reload: `systemctl restart docker` |
| Il disco del registry si riempie anche dopo aver cancellato i tag | Mancano `REGISTRY_STORAGE_DELETE_ENABLED=true` e la **garbage collection** |

## Perché è rilevante per l'SRE

- **Tempo di rilascio e di ripristino.** Immagini piccole e cache corretta riducono build, pull e quindi il tempo per riportare in piedi un servizio. Un nodo Kubernetes nuovo che scarica 1 GB di immagine impiega minuti; 40 MB, secondi.
- **Superficie d'attacco e conformità.** Ciò che non è nell'immagine non può essere sfruttato: niente compilatori, shell o `curl` a runtime. Gli scanner (Trivy, Grype) producono meno CVE su immagini piccole, e questa lezione è la base per il *supply chain security*.
- **Riproducibilità.** `package-lock.json` + base con versione fissata + tag immutabili + digest = stesso input, stessa immagine, rollback deterministico. È ciò che distingue un deploy che sai spiegare da uno "che funzionava ieri".
- **Il registry è infrastruttura critica.** Se è giù, non parte nessun nuovo Pod e nessun rollout; se è pieno, le pipeline falliscono. Ha bisogno di monitoraggio, backup, retention e controllo accessi, come qualunque altro servizio di produzione.
- **Catena di fiducia.** Il problema `x509 ... unknown authority` si ripresenta in Kubernetes, CI, proxy aziendali. Aver capito chi si fida di chi (CA, SAN, `certs.d`) ti fa risparmiare ore di diagnosi.
- **Costi.** Ogni pull da internet e ogni GB nel registry cloud ha un costo: la cache di build e i layer condivisi sono anche FinOps.
